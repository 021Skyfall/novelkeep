# 스위트북 과제 통합 계획

## 확정 사항

- 서비스명: 노벨킵(NovelKeep)
- 프로젝트 디렉터리명: `novelkeep`
- 주제: 완결 조건부 웹소설 소장본 펀딩 서비스
- 주요 타겟: 미완결 위험 없이 좋아하는 웹소설을 실물로 소장하려는 20~30대 독자
- 보조 사용자: 소장본 수요를 확인하고 완결 후 추가 수익을 얻으려는 독립 웹소설 작가
- 콘텐츠(연재·열람)가 본체이고, 책 제작 주문은 부가 기능이다.
- 흐름: 작품·회차 연재 → 소장본 펀딩(모의 결제) → 완결·목표 달성 → 책 주문 → 제작 상태
- 작품은 기본 권(부) `본편` 1개로 시작하며, 작가는 작품 상세에서 권(부)·회차를 추가·수정·삭제한다.
- 권(부) 구성을 별도 상태로 저장하지 않고 실제 권(부) 행이 1개면 한 권, 2개 이상이면 여러 권으로 표시한다. 각 부는 소장본 한 권의 출판 단위다.
- 권(부) `UNPUBLISHED(미공개)`는 소유자·관리자에게만 보이고, 독자·비소유 작가에게는 해당 권 섹션과 그 안 회차가 모두 미노출이다.
- 회차 공개·미공개는 부·작품 연재/완결 상태를 자동으로 바꾸지 않는다. 부 완결은 작가가 명시적으로 저장할 때만 변경되며, 그때 회차 전부 공개 여부를 검증한다.
- 작가는 일반 소설 1권 분량(약 8~10만 자) 안내를 보고, 초과 시 출판 협의(문의) 안내만 본다. 분량은 성공 조건이 아니다.
- 안전장치: 기한, **부 완결**, **목표 권수(최소 10)**. 미충족 시 환불(모의). 미공개 부에는 펀딩 개설 불가.
- 결제·환불은 실제 PG 없이 화면·상태만 모의 처리한다.
- 실제 인쇄 API, 배송, 회원 인증은 구현하지 않는다.
- 독자·작가·운영자(ADMIN) 역할별 고정 체험 회원을 하나씩 두고 랜딩페이지에서 선택한 회원을 세션에 저장한다.
- 공개 콘텐츠도 랜딩에서 역할을 선택한 뒤에만 접근한다. 독자·작가는 같은 콘텐츠 원본을 조회한다.
- `역할 변경`은 세션 로그아웃으로 처리하고, 다른 역할은 랜딩에서 다시 고른다.
- 랜딩페이지와 메인페이지는 분리한다.
- 메인페이지는 독자·작가에 같은 작품 탐색 본문을 제공하고, 작가에게만 내 작품 메뉴를 추가한다.
- 운영자는 주문 대시보드만 사용한다. 독자·작가 누적 메뉴는 붙이지 않는다.
- 독자는 `작가 권한 활성화 체험`으로 작가 고정 회원으로 전환할 수 있다. 작가→독자 되돌리기 버튼은 두지 않는다.
- 운영자는 전체 주문 조회·상태 변경·CSV/JSON 내보내기를 사용한다. 운영 통계(A-01)는 Lv2에서 보강한다.
- Docker로 외부 의존 없이 실행한다.
- 웹툰은 이번 과제 범위 밖이며, 향후 확장으로만 명시한다.
- `README.md`는 심사자용 최종 문서, `docs/`는 개발 과정·판단 근거로 분리한다.

## 데모·권한·소유권 결정 이유

- 과제에서 회원가입·로그인을 제외한 이유는 콘텐츠·펀딩·주문 핵심 흐름 검증에 집중하기 위해서다. 역할 선택은 보안 인증이 아니다.
- 역할별 고정 체험 회원 1명을 쓰는 이유는 재접속 후에도 같은 소유 데이터를 이어서 보고, 역할 선택마다 회원을 만들면 데이터가 분산되기 때문이다.
- 세션에 회원 ID와 역할을 함께 저장하는 이유는 역할만으로는 누가 작성한 작품인지 구분할 수 없기 때문이다. 역할은 메뉴·기능 범위, 회원 ID는 수정·삭제 소유권에 사용한다.
- 모든 역할이 같은 공개 콘텐츠를 보는 이유는 웹소설 탐색이 서비스 본체이고, 역할별 화면을 같은 데이터로 비교할 수 있어야 하기 때문이다.
- 공통 메인을 쓰는 이유는 역할마다 다른 홈을 만들면 플랫폼이 아니라 역할별 관리 도구처럼 보이기 때문이다. 관리 기능은 메뉴로만 추가한다.
- 독자→작가 단방향 체험만 두는 이유는 누구나 작가가 될 수 있다는 흐름을 보여주되, 작가는 이미 독자 기능을 포함하므로 되돌릴 필요가 없기 때문이다.
- 실서비스에서는 펀딩 피해 방지를 위해 작가 전환에 본인·작품 활동 인증이 필요하지만, 과제에서는 외부 인증 없이 체험만 제공한다.
- 독자 화면을 다시 보려면 `역할 변경`으로 로그아웃한 뒤 랜딩에서 독자를 선택한다.
- 라이트·다크 모드 전환은 사용자 선호로 제공한다. 최초 방문은 라이트 모드로 고정하고 이후 선택만 브라우저에 저장한다.
- 펀딩에 기한·완결·분량·수량 조건을 함께 둔 이유는 목표 수량만으로 미완결 작품을 출판하면 독자 피해와 작가·플랫폼 신뢰 문제가 생기기 때문이다.

## 주제 선택 이유

- 웹소설은 인쇄 없이도 독립적으로 소비되는 콘텐츠다.
- 완결 조건부 펀딩으로 미완결 구매 위험을 줄이고 작가 완결 동기를 만든다.
- 스위트북 Book Print API의 B2B 파트너 서비스(콘텐츠 플랫폼) 사례로 설명할 수 있다.
- 과제에서는 독립 소형 서비스로 구현하고, 기존 웹소설 플랫폼 연동은 확장안으로만 둔다.
- `웹소설 + 펀딩 + 종이책` 자체는 시장에 유사 사례가 있으나, 연재 중 펀딩·완결 전 출판 금지·자동 환불·주문 전환을 한 흐름으로 묶는 점이 과제용 차별점이다.

## 목표 레벨과 Phase 구분

- Phase는 환경·골조 준비 단위다. Phase 1은 Maven·Docker·MariaDB 실행 환경이다.
- Lv는 과제 평가 레벨이다.
  - Lv1 필수: 작품·부·회차 CRUD와 열람
  - Lv2 필수: 펀딩 참여(모의 결제), 목표·완결 판정, 책 주문·상태
  - Lv3 최선: 빈 목록·오류·모바일 독서 UX와 README 판단 기록
- Lv3 UX는 Lv1·Lv2 완료 후 별도로 시작하는 단계가 아니라, 각 기능 화면을 구현할 때 반응형·빈 상태·오류 안내·비동기 탐색과 판단 기록을 함께 적용하는 누적 평가 항목이다.
- 현재는 Phase 1과 Lv1을 완료했다. **독자·작가 범위 정리 완료.** 운영자 주문 대시보드(`/admin/orders`)는 시드 주문으로 1차 구현했고, 통계·실펀딩 전환 연동은 Lv2에서 보강한다. Lv3 공통 UX는 병행 적용 중이며, **다음은 Lv2 펀딩 참여·주문**이다.

## 기술 스택 결정

| 항목 | 선택 | 상태 |
|---|---|---|
| 언어 | Java 21 | 확정 |
| 프레임워크 | Spring Boot 4.1.0 | 확정 |
| 빌드 | Maven 3.9.16 | 확정 |
| 데이터 접근 | Spring Data JPA | 확정 |
| DB | MariaDB 11.8.8 LTS | 확정 |
| 화면 | Thymeleaf + JavaScript + Bootstrap 5.3.8 | 확정 |

### 버전 결정 기준

- 먼저 최신성과 운영 안정성의 균형을 기준으로 Java 21을 실행 환경으로 정했다.
- Java 21을 공식 지원하는 최신 안정 버전인 Spring Boot 4.1.0을 선택했다.
- Java 21에서 실행되고 Spring Boot 4.1.0의 요구 조건을 충족하는 최신 안정 버전인 Maven 3.9.16을 선택했다.
- 따라서 Java를 기준으로 호환성을 확인한 뒤 Spring Boot와 Maven의 최신 안정 버전을 확정했다.

### Java 21 선택 이유

- 장기 지원(LTS) 버전이며 2023년 출시 후 충분한 운영 사례가 축적됐다.
- 기존 시스템과 연동하지 않는 신규 독립 앱이라 과거 Java 버전과의 호환 제약이 없다.
- Spring Boot 4.1.0이 Java 21을 공식 지원하고 외부 라이브러리 호환 범위도 넓다.
- Java 17보다 최신이면서 Java 25보다 운영 검증 기간이 길어 최신성과 안정성의 균형이 좋다.
- 최신 버전 자체보다 과제에서 사용할 기술의 호환성과 설명 가능성을 우선했다.

### Spring Boot 4.1.0 선택 이유

- 2026년 7월 기준 최신 안정 버전이며 Java 21을 공식 지원한다.
- 새 프로젝트이므로 지원이 끝나 가는 이전 세대보다 현재 안정 버전을 선택해 바로 업그레이드할 부담을 줄였다.
- Spring MVC, JPA, Thymeleaf처럼 이번 과제에서 사용하는 표준 기능이 공식 Starter로 제공된다.
- 의존성 버전을 함께 관리하고 내장 Tomcat과 실행 JAR를 제공해 별도 WAS 설치 없이 동일한 실행 환경을 만들 수 있다.
- 최신 버전 자체가 목적은 아니며, 레거시 라이브러리 호환 문제가 없는 신규 프로젝트라 선택했다.

### Spring Framework만 사용하지 않은 이유

- 의존성 버전, 웹 설정과 WAS 배포 구성을 직접 맞추는 작업보다 과제의 콘텐츠·펀딩 로직 구현에 집중하기 위해서다.

### Maven 선택 이유

- 2026년 7월 기준 Maven 3의 최신 안정 버전을 사용한다.
- Gradle은 이전 빌드 결과를 재사용하고 바뀐 부분만 다시 처리해 큰 프로젝트에서 빠를 수 있다.
- 이번 과제는 작은 단일 프로젝트라 두 도구의 빌드 속도 차이가 크지 않다.
- `pom.xml`이 명시적이라 의존성과 빌드 단계를 면접에서 설명하기 쉽다.
- 사용자 사용 경험이 있고 현재 환경에 설치되어 있다.

### Gradle을 선택하지 않은 이유

- Gradle은 설정 파일에 조건과 동작을 프로그램처럼 자유롭게 작성할 수 있다.
- 이번 과제에는 복잡한 빌드 동작이 필요하지 않아 자유로운 설정보다 Maven의 정해진 구조가 이해하기 쉽다.

### JPA 선택 이유

- 작품·회차·펀딩·주문 대부분이 단순 CRUD다.
- `작품 1:N 회차`, `펀딩 1:N 참여`처럼 관계를 객체로 표현하기 쉽다.
- Mapper·XML 작성량보다 Repository 코드가 짧아 마감에 유리하다.
- 완결·목표 달성 판단은 Service에서 처리하므로 복잡한 SQL이 필수는 아니다.
- 관리자 통계는 소수의 집계 조회이므로 DTO Projection과 JPQL 또는 필요한 경우 Native Query로 처리할 수 있다.
- 주문 CSV·JSON도 조회 결과를 DTO로 변환해 내보내므로 데이터 접근 기술을 변경할 이유가 되지 않는다.

### MyBatis를 선택하지 않은 이유

- SQL을 직접 통제하는 장점은 있지만, 이번 범위의 조회는 복잡하지 않다.
- 같은 CRUD를 Mapper와 XML로 반복 작성하면 속도가 느려진다.
- N+1 가능성은 목록 DTO 조회와 SQL 로그로 검증한다.
- 동적 보고서와 복잡한 통계가 핵심인 서비스가 아니므로 JPA와 MyBatis를 혼용하지 않는다.

### MariaDB 선택 이유

- 사용 경험이 있고 Docker Hub 공식 이미지로 심사자가 `docker-compose up`만으로 실행할 수 있다.
- 2026년 7월 기준 LTS 계열의 최신 패치인 11.8.8 공식 이미지를 고정해 실행 환경 차이를 줄인다.
- 펀딩·주문 상태처럼 영속 데이터와 제약조건을 실제 DB로 검증하기 좋다.
- 이번 범위에 PostgreSQL·Oracle의 고급 기능은 필요하지 않다.

### H2를 선택하지 않은 이유

- 제출은 편하지만 운영 DB와 SQL 동작이 다를 수 있다.
- 실무 유사성과 상태 데이터 검증을 우선했다.

### Thymeleaf 선택 이유

- 이번 화면은 목록·상세·입력 폼 중심이라 별도 SPA가 필요하지 않다.
- Controller가 화면 이름과 데이터를 전달하고, 템플릿이 실행 JAR에 함께 포함된다.
- 별도 Node 빌드·프론트 서버·CORS 설정 없이 앱과 DB 두 컨테이너만 구성할 수 있다.
- 동적 상태 표시와 모의 결제 확인은 필요한 부분만 JavaScript로 처리한다.

### Bootstrap 5.3.8 선택 이유

- 과제 안내문이 기성 UI 라이브러리 사용을 권장하고 디자인 감각보다 사용자 흐름의 근거를 평가한다.
- 공식 목록·카드·폼·버튼·진행률·배지·모달 컴포넌트를 그대로 활용해 화면 제작 시간을 줄인다.
- 반응형 Grid와 유틸리티 클래스로 독자용 모바일 화면을 빠르게 구성한다.
- CDN은 사용하지 않고 버전을 고정한 CSS·JavaScript를 앱의 로컬 정적 자원으로 제공한다.
- 커스텀 CSS는 웹소설 본문 가독성과 필요한 화면 보정에만 최소로 사용한다.

### React / Vue / JSP를 선택하지 않은 이유

- React·Vue는 프론트 빌드와 API 연동이 늘어 일정 위험이 크다.
- JSP는 Spring Boot 내장 서버와 패키징 설정이 더 번거롭다.

## 확정 스택 요약

`Java 21 + Spring Boot 4.1.0 + Maven 3.9.16 + Spring Data JPA + MariaDB 11.8.8 LTS + Thymeleaf + JavaScript + Bootstrap 5.3.8 + Docker Compose`

## 패키지 구조

- 기능 수정 위치를 쉽게 찾을 수 있도록 계층 우선이 아닌 도메인 우선 구조를 사용한다.
- 기본 형식은 `com.novelkeep.{도메인}.{계층}`이다.
- 주요 도메인은 `home`, `member`, `novel`, `funding`, `order`, `admin`으로 구분한다.
- 각 도메인 안에서 필요한 경우에만 `controller`, `service`, `repository`, `domain`, `dto`를 만든다.
- 구현하지 않은 도메인의 빈 패키지는 미리 만들지 않는다.

```text
com.novelkeep
├─ home          # 현재: controller, domain(ExperienceRole)
├─ member        # 현재: domain, repository, service
├─ novel         # 예정
├─ funding       # 예정
├─ order         # 예정
└─ admin         # 예정
```

현재 구현된 도메인만 패키지를 두고, 나머지 도메인은 실제 구현할 때 만든다.
## Docker 실행 구조

- Docker Compose를 선택한 이유는 심사자가 로컬 Java·Maven·MariaDB를 설치하지 않고도 동일 환경으로 재현 실행할 수 있기 때문이다.
- 심사자는 호스트 PC에서 저장소를 클론하고 `docker compose up --build`를 실행한다.
- Docker가 Maven 3.9.16·Java 21 빌드 이미지로 JAR를 만든 뒤 Java 21 런타임 이미지에서 앱을 실행한다.
- MariaDB 11.8.8은 별도 컨테이너로 실행하고 DB healthcheck 통과 후 앱을 시작한다.
- 앱 컨테이너는 Compose 내부 네트워크에서 `db:3306`으로 MariaDB에 연결한다.
- IDE에서 앱을 직접 실행할 때는 `localhost:3307`로 MariaDB 컨테이너에 연결한다.
- 호스트 DB 포트 3307은 기존 MySQL·MariaDB의 기본 포트 3306과 충돌하지 않도록 선택했다.
- Compose 환경변수에는 과제용 기본값이 있어 별도 `.env` 파일 없이 실행할 수 있다.
- `.env`는 앱·DB 포트를 변경할 때만 선택적으로 만들며 Git에는 포함하지 않는다.
- 개발·데모 단계는 Hibernate `create-drop`으로 앱 시작 시 스키마를 새로 만들고 종료 시 제거한다.
- 현재 구현된 목 데이터는 `DemoDataInitializer` 한 곳에서 체험 회원 → 작품·부·회차 순으로 자동 적재한다.
- Maven Wrapper는 Docker 빌드와 로컬 Maven 3.9.16이 있어 사용하지 않는다.

## 작품 CRUD·탐색 UX 구현 내용

- `/novels`는 공개 탐색 전용이다. 독자·작가는 `PUBLIC`만 보고, 관리자만 미공개 필터를 사용할 수 있다.
- `/writer/novels`는 소유 작품 관리 화면으로 분리한다. 공개 여부·연재 상태(연재 중/부 완결/전체 완결)·제목 검색을 제공한다.
- 연재 중 검색은 부 완결이 있어도 포함한다. 부 완결은 연재 중이면서 완결 부가 있는 작품만, 전체 완결은 작품 상태 `COMPLETED`다.
- 목록 배지는 최신 완결 부 번호(`1부 완결`)를 표시한다.
- 추천은 공개 작품만, 자신의 작품은 차단한다. 추천 수 변경은 작품 수정일(`updated_at`)을 건드리지 않는다.
- 내 즐겨찾기는 공개 작품 토글이며 `/novels?favorite=true`로 조회한다.
- 추천·내 즐겨찾기 토글과 검색·필터·페이지 이동은 AJAX 부분 갱신으로 처리하고, URL 이력과 브라우저 뒤로·앞으로 이동을 유지한다.
- 독자→작가 체험 전환은 고정 회원이 바뀌어 즐겨찾기·추천·책갈피 데이터가 이어지지 않는다. 연속성 테스트 중에는 역할 전환을 권장하지 않는다.
- 수정 취소는 작품 상세로, 삭제 확인은 되돌릴 수 없음 안내를 포함한다.

## 다중 장르·이어읽기 선택 근거

- 회차 번호는 `episodeNumber`가 담당하므로 제목에는 순수 제목만 저장한다. 시드·입력 예시에 `1화.`를 넣으면 화면에서 `1화. 1화. …`처럼 중복된다.
- 작품 장르는 최소 1개·최대 8개로 제한한다. 탐색·등록과 카드 태그 펼침을 함께 맞추기 위한 상한이다.
- 장르 enum은 유지하고 `novel_genre` 컬렉션 테이블에 저장한다. 임의 문자열을 차단하면서 다중 값을 표현하기 위해서다.
- 검색 장르는 다중 선택이며, 선택 장르를 **모두** 가진 작품만 조회한다(AND). OR는 결과가 넓어져 탐색 의도가 흐려지기 쉽다.
- 장르 UI는 드롭다운 대신 접이식 배지를 쓴다. 50종을 한 번에 펼치면 부담이 커서 주요 장르만 기본 표시하고 `전체 장르`로 펼친다.
- 배지 선택값은 반복 `genres` 파라미터로 유지해 AJAX 검색·페이지 이동·뒤로가기에서도 같은 조건을 복원한다. 공통 `novel-search.js`는 수정하지 않고 전용 스크립트가 폼 submit만 호출한다.
- 책갈피는 회원별·작품별 1개다. 읽는 위치를 하나만 기억하면 이어읽기 CTA가 단순해지고 `(member_id, novel_id)` 유일 제약으로 구현할 수 있다.
- 같은 회차에서 다시 누르면 해제하고, 다른 회차에서 누르면 위치를 덮어쓴다. 작품 상세에는 `N화부터 이어 읽기`를 제공한다.
- 회차·권(부)이 미공개가 되거나 작품이 미공개로 바뀌면 권한 없는 사용자에게 이어읽기만 숨기고 데이터는 보존한다. 물리 삭제(회차·부·작품) 시에만 관련 책갈피를 먼저 삭제한다.

## 단계별 목 데이터 정책

- 모든 도메인의 데이터를 미리 만들지 않고 기능 구현 단계에 맞춰 추가한다.
- 작품·회차 단계: 역할별 체험 회원 3명, 작품 50건, 부 132건, 회차 1,177건(작품당 20~27화)을 한 초기화 클래스에서 생성한다.
- 완결작은 모두 3개 완결 부(3권)와 공개 회차를 가지며, 연재작은 완결 부→연재 부→집필 중 부 순서를 유지한다.
- 다중 부는 부당 7~9화로 구성하고 공개·미공개와 소유자를 분산한다. 소설 분야 50종은 공통 `NovelGenre` enum이며 작품당 **2~8개** 장르를 배분해 카드 태그 `...` 펼침을 확인할 수 있게 한다.
- 추천과 즐겨찾기는 사용자가 직접 추가·해제하는 흐름을 확인할 수 있도록 초기값을 각각 0건으로 둔다.
- 회차 CRUD·열람 단계에서는 현재 목 회차를 화면과 Service에 연결한다.
- 펀딩 단계: 진행·성공·실패·환불 데이터를 추가한다.
- 주문 단계: 접수·제작 중·제작 완료 데이터를 추가한다.
- 앱 재시작마다 `create-drop`으로 초기화하므로 이전 실행에서 변경한 데이터는 유지하지 않는다.

## Lv1 메인 쇼케이스·네비게이션 정리

- 메인의 인기작·새 회차·완결 몰아보기는 공개 DB 데이터와 연결한다. 인기 추천순 10, 신작 최신 10, 완결 10건. 카드 클릭 시 작품 상세 또는 회차 열람으로 이동한다.
- 각 벨트는 무한 가로 슬라이드로 약 5초마다 한 칸 이동하며, 마우스·터치 드래그와 클릭 이동을 함께 지원한다. 슬라이드 개수 표시는 두지 않는다.
- 소장본 펀딩 벨트는 진행 중 OPEN 캠페인 최대 5건을 같은 슬라이드로 노출하고 `/fundings/{id}` 상세(읽기 전용)로 연결한다. 참여·주문은 Lv2.
- 상단 탭은 모두 메인 앵커로 통일한다. 홈(`/main`), 인기작(`/main#popular`), 신작(`/main#new`), 완결작(`/main#completed`), 소장본 펀딩(`/main#funding`).

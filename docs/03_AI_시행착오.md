# AI 활용 및 시행착오

## 사용 도구

- Cursor: 과제 안내문 분석, 단계별 의사결정 보조와 환경 확인
- AI가 `winget`과 WSL 명령을 실행해 Docker Desktop 설치를 보조함
- 사용자가 재부팅 후 WSL 알림과 Docker Desktop 실행을 확인함

## 가장 크게 느낀 점: 협업의 핵심은 의사소통

AI를 전 과정에 활용한 바이브 코딩에서 가장 힘들었던 부분은 코드 작성 자체가 아니라, 내가 생각한 결과와 AI가 해석해 만든 결과의 차이를 계속 찾아 수정하는 일이었다. AI는 구현 속도가 빠르지만 짧은 지시의 빈 부분을 일반적인 관례로 채우기 때문에, 서비스의 맥락·화면의 의미·데이터 상태·사용자가 기대하는 동선이 충분히 전달되지 않으면 빠른 속도만큼 재작업도 빠르게 늘어났다.

이 경험을 통해 협업 상대가 사람이든 AI든 가장 중요한 것은 결국 의사소통이라는 점을 크게 느꼈다. 같은 용어를 사용해도 서로 머릿속에 그리는 화면과 동작은 다를 수 있으며, “직관적으로”, “공통으로”, “한 단계 뒤로” 같은 표현도 구체적인 예시와 완료 조건이 없으면 다르게 해석될 수 있다. 상대의 구현 능력만큼 요구사항을 정확히 설명하고, 중간 결과를 확인하고, 어긋난 이유를 다시 공통 언어로 정리하는 과정이 중요했다.

효율적인 협업을 위해서는 구현 전에 목적과 사용자 흐름을 먼저 맞추고, 모호한 부분은 실제 URL·버튼 문구·전후 화면·데이터 예시로 구체화해야 한다. 또한 한 번 결정한 내용은 요구사항·화면 정의·데이터 모델 문서에 남겨 다음 작업의 공통 기준으로 사용해야 한다. 작은 단위로 구현하고 바로 화면과 로그를 검증하는 피드백 루프도 재작업 범위를 줄이는 데 필요했다.

결국 AI는 지시를 그대로 실행하는 자동 코딩 도구라기보다, 맥락을 공유하고 결과를 함께 조율해야 하는 협업자에 가까웠다. AI를 많이 사용하는 것만으로 개발이 쉬워지는 것은 아니며, 사용자가 서비스의 방향과 완료 기준을 분명히 세우고 지속적으로 소통할 때 속도와 품질을 함께 얻을 수 있다는 것이 이번 프로젝트에서 얻은 가장 큰 배움이다.

## 바이브 코딩의 부수 효과: 작업 중 얻는 기술 지식

의사소통·재작업뿐 아니라, AI가 문제를 고치는 과정을 옆에서 보면 평소에 접하지 않던 프론트엔드·브라우저 동작 지식을 자연스럽게 배우게 되는 면도 있었다. 예를 들어 메인 가로 슬라이드에서 클릭은 되는데 드래그가 한두 번 뒤 끊기는 현상을 고칠 때, AI가 `dragstart` 기본 동작 차단과 카드 링크의 `draggable="false"`를 적용한다고 설명했고, 이 기법은 사전에 알지 못했던 내용이었다.

카드가 `<a href>`이면 마우스 드래그 시 브라우저가 “링크 URL을 드래그하는 네이티브 동작”으로 가로챌 수 있다. 그 순간 화면에는 URL 고스트가 뜨고, 우리가 만든 슬라이드 이동 로직은 포인터를 잃는다. 클릭과 드래그를 한 요소에서 같이 쓰려면 다음을 구분해야 한다.

- 클릭 이동: 작은 움직임은 무시하고(임계값), 드래그로 판정되지 않았을 때만 링크 기본 이동을 허용한다.
- 슬라이드 드래그: 임계값을 넘긴 뒤에만 커스텀 오프셋을 갱신한다.
- 네이티브 링크 드래그 차단: `draggable="false"`, `dragstart`에서 `preventDefault`, CSS `-webkit-user-drag: none`으로 URL 드래그를 막는다.
- 미세 흔들림으로 클릭이 막히는 문제: `pointermove` 1px만으로도 “드래그했다”고 보면 `click`을 막아 페이지 이동이 실패한다. 임계값(예: 8px) 이후에만 드래그로 본다.

이처럼 AI 협업의 장점은 구현 속도만이 아니라, 버그 원인과 해결 수단이 대화로 드러나면서 브라우저·DOM 지식을 축적할 수 있다는 점에도 있다. 다만 설명만 듣고 넘어가면 휘발되므로, 핵심 API와 “왜 필요한지”는 이 문서처럼 짧게라도 남겨 다음 유사 UI에 재사용한다.

## 실패와 수정

- AI가 기본 기획안인 `학급알림장`과 권장 기술 조합을 확정 사항처럼 안내함
- 사용자가 아직 정하지 않았음을 지적함
- 주제, 타겟 사용자와 기술 스택을 모두 미확정 상태로 되돌리고 프로젝트 규칙에 명시함
- 사용자가 사업 관점(펀딩·완결 조건·B2B)을 주도하고 AI는 과제 범위와 시장 유사 사례를 교차 검증함
- 시장 최초라고 단정하지 않도록 수정하고, 차별점은 `연재+완결 조건부 펀딩+주문 전환` 통합으로 한정함
- AI가 기존 설치 환경을 우선해 Java 17을 제안했으나, 사용자가 독립 신규 앱에는 최신 LTS를 선호한다고 판단함
- Java 25의 짧은 운영 기간과 외부 라이브러리 호환 위험을 다시 비교함
- 최신성과 검증된 운영 사례의 균형을 위해 Java 21로 최종 변경함
- AI가 인증 제외 조건을 회원 데이터 제외로 과도하게 해석해 첫 ERD에서 회원을 누락함
- 사용자가 작품·펀딩·주문 소유권 문제를 발견해 로그인 없는 최소 회원 엔티티를 추가함
- 권의 시작·종료 번호만 저장하던 초안을 권-회차 연결 테이블 방식으로 수정해 여러 권 구성을 명확히 함
- 사용자가 부 구분을 작가 선택으로 변경해, nullable FK 대신 숨겨진 기본 부 `본편`을 자동 생성하는 방식으로 수정함
- 상태상 값이 없는 공개·환불·완료 시각만 NULL을 허용하고 나머지는 NOT NULL로 정리함
- AI가 역할별 화면 구조를 `각 역할의 첫 기능 화면을 메인처럼 사용`하는 방식으로 해석한 뒤, 다시 `공통 역할 탭으로 전환`하는 방식으로 수정해 사용자의 의도와 연속해서 어긋남
- 사용자가 원한 구조는 `별도 랜딩페이지에서 역할 선택 → 공통 메인 경로와 템플릿 사용 → 세션 역할에 따라 메인 메뉴와 본문을 다르게 렌더링`하는 방식이었음
- AI가 `랜딩페이지`, `메인페이지`, `역할별 기능 화면`의 구분을 먼저 확인하지 않고 문서에 반영해 반복 수정이 발생함
- 이후 사용자가 같은 내용을 여러 번 질문하거나 지시·정정하면 단순 보완이 아닌 AI 시행착오로 판단하고, 원래 해석·사용자 수정·최종 결정·재발 방지를 이 문서에 별도 요청 없이 기록하기로 함
- AI가 서비스 특성 설명에 치우친 딱딱하거나 의미가 불분명한 이름을 반복 제안해 사용자가 원하는 `스위트노벨처럼 짧고 부드러운 이름`과 맞지 않았음
- 사용자가 후보의 방향을 단계적으로 좁힌 뒤 직관성과 발음을 우선해 서비스명을 `노벨킵(NovelKeep)`으로 최종 결정함
- AI가 Lv3 화면·UX 정의까지 합의한 뒤에도 목표 레벨 승인을 남은 절차로 잘못 안내함
- 사용자가 화면 정의가 이미 Lv3 목표를 전제로 한다고 확인해 목표 레벨을 Lv3으로 확정하고, `기획 완료`와 `실제 구현 완료`는 구분해 기록함
- 확장 프로그램 일괄 설치에 현재 PowerShell이 지원하지 않는 `&&`를 사용해 구문 오류가 발생함
- PowerShell 배열 반복 방식으로 수정해 Java·Spring Boot·Maven·Docker·YAML 확장 설치를 완료함
- Thymeleaf 스니펫 확장은 Cursor 저장소에서 찾을 수 없어 검증되지 않은 VSIX 설치로 우회하지 않고 기본 HTML 지원과 Spring 확장을 사용하기로 함
- AI가 Maven Wrapper를 심사 환경의 빌드 재현 수단으로 먼저 추가했으나 심사자는 Docker만 실행하고 Docker 빌드에서 Maven 3.9.16 이미지를 사용할 예정이라 중복이었음
- 사용자가 실행 주체와 Docker 빌드 방식을 다시 확인해 `mvnw`, `mvnw.cmd`, `.mvn/`과 관련 README 설명을 제거함
- AI가 Docker 실행 흐름에서 호스트와 컨테이너의 경계를 충분히 명확히 설명하지 않아 사용자가 Git clone과 Compose 명령도 Docker 내부에서 실행한다고 이해함
- 실제 흐름은 심사자 호스트에서 Git clone과 `docker compose up`을 실행하고, Docker가 Maven 빌드 이미지와 실행 컨테이너를 내부에서 생성하는 방식으로 다시 구분함
- DB Volume 지속성 검증용 SQL을 컨테이너 셸 환경변수와 함께 실행하다 PowerShell 따옴표 충돌로 SQL이 잘림
- 검증 전용 계정을 명시한 단순 명령으로 수정해 테스트 데이터를 생성하고 재시작 후 유지 여부를 확인함
- 처음에는 환경변수 변경 예시를 위해 `.env.example`을 만들었으나 사용자가 현재 값은 민감하지 않고 별도 파일 없이 실행되는 구성을 원함
- Compose에 과제용 기본값을 유지하고 `.env.example`은 제거했으며, `.env`는 포트 변경 시에만 선택적으로 생성하도록 README를 수정함
- 역할별 메인 제목에 Thymeleaf 리터럴 치환 구분자와 같은 `|` 문자를 넣어 템플릿 파싱 500 오류가 발생함
- 리터럴 치환 대신 문자열 결합식으로 제목을 렌더링하도록 수정함
- 역할 미선택 `/main` 요청에서도 `HttpSession`을 새로 만들어 리다이렉트 URL에 세션 ID가 붙고 자동 이동 검증이 실패함
- `request.getSession(false)`로 기존 세션만 조회하고 쿼리 파라미터로 안내하도록 수정해 불필요한 세션 생성을 막음
- AI가 `역할에 따라 메인을 다르게 렌더링`한다는 결정을 역할별로 메인 본문 전체를 교체하는 방식으로 구현함
- 사용자가 원한 구조는 모든 역할이 같은 웹소설 탐색 메인을 사용하고 작가에게 `내 작품`, 관리자에게 `운영·주문 관리`처럼 권한별 메뉴만 추가하는 방식이었음
- 역할은 콘텐츠 접근 화면을 분리하는 기준이 아니라 추가 관리 기능을 노출하는 권한으로 사용하고, 작가·관리자도 독자와 같은 작품 탐색·열람 화면을 이용하도록 수정하기로 함

### 요구사항 해석 차이로 발생한 디테일 재작업

- 공통 원인: AI가 기능 명칭이나 짧은 지시를 일반적인 서비스 관례로 보완해 구현했지만, 사용자가 생각한 화면 의미·데모 데이터 상태·출판 정책과 달라 작은 수정이 연속해서 발생함
- 영향: 개별 기능은 동작해도 사용자가 직접 화면과 데이터를 확인한 뒤 의도를 다시 설명해야 했고, CSS·목 데이터·문서까지 같은 내용을 여러 차례 고치면서 핵심 기능 개발보다 디테일 조정에 시간이 오래 걸림

- 예시 1 — 역할별 메인과 메뉴
  - AI 구현: 역할마다 메인 본문을 다르게 구성하고 독자 메뉴·작가 메뉴 제목과 역할 전환 안내를 화면에 표시함
  - 사용자 의도: 모든 역할이 같은 작품 탐색 메인을 사용하고 상위 역할에는 관리 메뉴만 누적하며, 체험 계정 데이터 단절 안내는 화면이 아니라 README에만 기록
  - 재작업: 공통 메인으로 통합하고 메뉴 제목·화면 경고를 제거했으며, 홈과 기능 화면의 메뉴 글자 크기·선택 상태·구분선까지 다시 통일함

- 예시 2 — 비동기 탐색의 로딩 표현
  - AI 구현: 검색 중 `불러오는 중` 문구를 일반 영역에 표시함
  - 사용자 의도: 목록 높이와 화면 위치가 움직이지 않는 짧은 `...` 표시
  - 재작업: 목록 내부 오버레이 형태로 변경하고, 검색 결과가 없을 때 스크롤바가 사라져 화면이 좌우로 움직이는 문제도 `scrollbar-gutter`로 추가 보정함

- 예시 3 — 체험 목 데이터의 초기 상태
  - AI 구현: 작품 60건·회차 1,512건과 함께 추천 데이터를 미리 생성했고, 미공개 작품 생성 규칙이 관리자 소유 규칙과 겹쳐 작가 화면에서는 미공개 작품이 없는 것처럼 보였음
  - 사용자 의도: 구형 심사 노트북에서도 부담이 적고, 추천·즐겨찾기는 모두 0에서 직접 조작하며, 작가와 관리자 양쪽에서 공개·미공개 상태를 현실적으로 확인할 수 있는 데이터
  - 재작업: 작품 50건·회차 1,177건으로 조정하고 추천·즐겨찾기를 0건으로 초기화했으며, 상태·소유자·공개 여부 규칙의 상관관계를 분리함

- 예시 4 — 부와 소장본 권의 관계
  - AI 구현: 부를 이야기 구간으로만 보고 한 부 안에서 다시 여러 출판 권으로 나눌 수 있는 정책을 문서에 남김
  - 사용자 의도: `1부=소장본 1권`, `2부=소장본 2권`처럼 부와 권을 1:1로 대응
  - 재작업: 단권/여러 권 구성으로 화면 표현을 바꾸고, 각 부를 한 권의 출판 단위로 요구사항·ERD·화면 정의서에 통일함

- 예시 5 — 장르 입력과 데이터 무결성
  - AI 구현: 장르를 자유 문자열 컬럼과 직접 입력 필드로 두어 오탈자나 임의 값이 저장될 수 있었음
  - 사용자 의도: 소설 장르를 공통 목록으로 관리하고 허용되지 않은 값은 저장 단계 전에 차단
  - 재작업: 소설 분야 50종을 `NovelGenre` enum으로 정의하고 등록·검색·목 데이터에서 함께 사용했으며, 임의 장르 요청이 HTTP 400으로 거부되는지 확인함

- 예시 6 — 회차 제목 번호 중복
  - AI 구현: 시드 제목에 `1화. …`를 넣고 상세·목록 템플릿에서도 `episodeNumber화. ${title}`로 조합해 `1화. 1화. …`가 표시됨
  - 사용자 의도: 번호는 `episodeNumber`가 담당하고 제목에는 순수 제목만 저장
  - 재작업: 시드·입력 placeholder에서 번호 접두를 제거하고 화면 조합만 유지함
  - 재발 방지: 표시용 접두사를 데이터에 넣지 말고, 템플릿 조합 규칙을 문서와 입력 안내에 함께 적는다

- 예시 7 — 단일 장르에서 다중 장르 AND로 재작업
  - AI 구현: 작품당 장르 1개와 드롭다운 검색으로 충분하다고 가정함
  - 사용자 의도: 작품당 최대 5개 장르, 접이식 배지 다중 선택, 선택 장르 모두 포함(AND)
  - 재작업: `novel_genre` ElementCollection, Specification AND, 전용 배지 JS/CSS로 교체하고 선택 근거를 요구사항·ERD·화면에 기록함

- 재발 방지: 화면 문구·초기 데이터·도메인 용어처럼 해석에 따라 결과가 달라지는 항목은 구현 전에 `현재 해석 → 구체 예시 → 데이터 상태`를 짧게 제시해 확인하고, 합의되지 않은 관례를 코드와 문서에 먼저 확정하지 않는다

### 권(부) 자동 판별 이후 회차 화면 지연 로딩 오류

- 발생 현상: 회차 작성·수정 화면에 접근하면 Whitelabel Error Page가 표시되고, 서버 로그에는 `Novel.parts`의 `LazyInitializationException`이 기록됨
- 원인: 별도 `PartMode`를 제거한 뒤 `Novel.isMultiPart()`가 실제 권(부) 목록 크기로 다권 여부를 계산하게 됐지만, 회차 조회 서비스가 트랜잭션 안에서 `Novel.parts`를 초기화하지 않은 채 엔티티를 반환함. Thymeleaf가 트랜잭션 종료 후 `novel.multiPart`를 평가하면서 지연 로딩에 실패함
- 수정: `findOwnedPart`, `findOwnedEpisode`, `findReadableEpisode`가 반환되기 전에 `Novel.parts`를 초기화하도록 서비스 조회 경계를 보완함. 컨트롤러 흐름과 Repository 쿼리는 변경하지 않음
- 검증: Maven 전체 테스트 후 Docker 앱 이미지를 재빌드하고, 작가 세션에서 회차 수정과 읽기 URL이 모두 HTTP 200인지 확인함. 재요청 후 애플리케이션 오류 로그가 발생하지 않는 것도 확인함
- 재발 방지: LAZY 연관 컬렉션을 사용하는 계산형 getter는 반드시 트랜잭션 안에서 필요한 데이터를 준비하거나 화면 전용 값으로 전달한다. 컴파일·단위 테스트 통과와 실행 컨테이너 반영은 별개이므로, 화면 변경 후에는 `docker compose up -d --build app`과 실제 URL 응답·서버 로그까지 함께 확인한다

### 회원·권한 설계 변경

- 초기 판단: 역할 선택마다 체험 회원을 새로 만들고 닉네임에 ID를 붙여 화면에 표시함
- 문제: 로그아웃 후 다시 들어오면 이전 작품 소유자를 이어갈 수 없고, 회원 ID·닉네임은 과제 데모에 불필요함
- 최종 결정: 역할별 고정 체험 회원 1명만 두고 재사용한다. 닉네임은 제거하고 화면에는 역할명만 표시한다. `UNIQUE(member_type)`과 앱 시작 목 데이터 생성으로 맞춘다
- 재발 방지: 회원가입·로그인을 제외해도 소유권 재진입이 필요한지 먼저 확인하고, 고정 회원 vs 매번 생성 중 하나를 문서에 명시한다

- 초기 판단: 세션의 role만으로 CRUD 접근을 구분하면 충분하다고 봄
- 문제: 역할만으로는 누가 작성한 작품인지 식별할 수 없고, 같은 역할이면 모든 작품을 수정하게 됨
- 최종 결정: 세션에 고정 `memberId`와 역할을 함께 저장한다. 역할은 기능 범위, 회원 ID는 소유권 검증에 사용한다
- 재발 방지: 권한과 소유권을 문서·Service에서 항상 분리해 적는다

- 초기 판단: 독자↔작가 빠른 양방향 전환 버튼을 두면 데모 검증이 편하다고 봄
- 문제: 작가는 이미 독자 기능을 포함하므로 되돌릴 필요가 없고, 버튼이 실서비스의 양방향 역할 전환처럼 오해됨
- 최종 결정: 독자→작가 체험만 유지하고 작가→독자 버튼은 제거한다. 독자 화면 재검증은 `역할 변경`(로그아웃) 후 랜딩 재선택으로 한다. 실서비스 작가 전환에는 펀딩 피해 방지를 위한 엄격한 인증이 필요함을 문서에 명시한다
- 재발 방지: 누적 권한 모델에서는 상위 역할의 하위 되돌리기 UI를 기본으로 만들지 않는다

- 초기 판단: 인증 제외를 회원 데이터 자체를 두지 않는 것으로 해석하거나, 반대로 역할 선택마다 회원 가입처럼 생성함
- 문제: 전자는 소유권을 못 잡고, 후자는 인증 없는 회원가입처럼 보임
- 최종 결정: 인증·비밀번호는 구현하지 않고, 역할별 고정 체험 회원으로 소유권만 구분한다. 역할 선택은 보안 인증이 아님을 README와 요구사항에 명시한다
- 재발 방지: “인증 제외”와 “소유자 식별용 최소 회원”을 같은 문장에서 구분해서 적는다

- 발생 현상 1: 카드 클릭으로 작품·회차 이동이 되지 않음

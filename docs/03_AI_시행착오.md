# AI 활용 및 시행착오

## 사용 도구

- Cursor: 과제 안내문 분석, 단계별 의사결정 보조와 환경 확인
- AI가 `winget`과 WSL 명령을 실행해 Docker Desktop 설치를 보조함
- 사용자가 재부팅 후 WSL 알림과 Docker Desktop 실행을 확인함

## 실패와 수정

- AI가 기본 기획안인 `학급알림장`과 권장 기술 조합을 확정 사항처럼 안내함
- 사용자가 아직 정하지 않았음을 지적함
- 주제, 타겟 사용자와 기술 스택을 모두 미확정 상태로 되돌리고 프로젝트 규칙에 명시함
- 사용자가 사업 관점(펀딩·완결 조건·B2B)을 주도하고 AI는 과제 범위와 시장 유사 사례를 교차 검증함
- 시장 최초라고 단정하지 않도록 수정하고, 차별점은 `연재+완결 조건부 펀딩+주문 전환` 통합으로 한정함
- AI가 기존 설치 환경을 우선해 Java 17을 제안했으나, 사용자가 독립 신규 앱에는 최신 LTS를 선호한다고 판단함
- Java 25의 짧은 운영 기간과 외부 라이브러리 호환 위험을 다시 비교함
- 최신성과 검증된 운영 사례의 균형을 위해 Java 21로 최종 변경함
- AI가 인증 제외 조건을 회원 데이터 제외로 과도하게 해석해 첫 ERD에서 회원을 누락함
- 사용자가 작품·펀딩·주문 소유권 문제를 발견해 로그인 없는 최소 회원 엔티티를 추가함
- 권의 시작·종료 번호만 저장하던 초안을 권-회차 연결 테이블 방식으로 수정해 여러 권 구성을 명확히 함
- 사용자가 부 구분을 작가 선택으로 변경해, nullable FK 대신 숨겨진 기본 부 `본편`을 자동 생성하는 방식으로 수정함
- 상태상 값이 없는 공개·환불·완료 시각만 NULL을 허용하고 나머지는 NOT NULL로 정리함
- AI가 역할별 화면 구조를 `각 역할의 첫 기능 화면을 메인처럼 사용`하는 방식으로 해석한 뒤, 다시 `공통 역할 탭으로 전환`하는 방식으로 수정해 사용자의 의도와 연속해서 어긋남
- 사용자가 원한 구조는 `별도 랜딩페이지에서 역할 선택 → 공통 메인 경로와 템플릿 사용 → 세션 역할에 따라 메인 메뉴와 본문을 다르게 렌더링`하는 방식이었음
- AI가 `랜딩페이지`, `메인페이지`, `역할별 기능 화면`의 구분을 먼저 확인하지 않고 문서에 반영해 반복 수정이 발생함
- 이후 사용자가 같은 내용을 여러 번 질문하거나 지시·정정하면 단순 보완이 아닌 AI 시행착오로 판단하고, 원래 해석·사용자 수정·최종 결정·재발 방지를 이 문서에 별도 요청 없이 기록하기로 함
- AI가 서비스 특성 설명에 치우친 딱딱하거나 의미가 불분명한 이름을 반복 제안해 사용자가 원하는 `스위트노벨처럼 짧고 부드러운 이름`과 맞지 않았음
- 사용자가 후보의 방향을 단계적으로 좁힌 뒤 직관성과 발음을 우선해 서비스명을 `노벨킵(NovelKeep)`으로 최종 결정함
- AI가 Lv3 화면·UX 정의까지 합의한 뒤에도 목표 레벨 승인을 남은 절차로 잘못 안내함
- 사용자가 화면 정의가 이미 Lv3 목표를 전제로 한다고 확인해 목표 레벨을 Lv3으로 확정하고, `기획 완료`와 `실제 구현 완료`는 구분해 기록함
- 확장 프로그램 일괄 설치에 현재 PowerShell이 지원하지 않는 `&&`를 사용해 구문 오류가 발생함
- PowerShell 배열 반복 방식으로 수정해 Java·Spring Boot·Maven·Docker·YAML 확장 설치를 완료함
- Thymeleaf 스니펫 확장은 Cursor 저장소에서 찾을 수 없어 검증되지 않은 VSIX 설치로 우회하지 않고 기본 HTML 지원과 Spring 확장을 사용하기로 함
- AI가 Maven Wrapper를 심사 환경의 빌드 재현 수단으로 먼저 추가했으나 심사자는 Docker만 실행하고 Docker 빌드에서 Maven 3.9.16 이미지를 사용할 예정이라 중복이었음
- 사용자가 실행 주체와 Docker 빌드 방식을 다시 확인해 `mvnw`, `mvnw.cmd`, `.mvn/`과 관련 README 설명을 제거함
- AI가 Docker 실행 흐름에서 호스트와 컨테이너의 경계를 충분히 명확히 설명하지 않아 사용자가 Git clone과 Compose 명령도 Docker 내부에서 실행한다고 이해함
- 실제 흐름은 심사자 호스트에서 Git clone과 `docker compose up`을 실행하고, Docker가 Maven 빌드 이미지와 실행 컨테이너를 내부에서 생성하는 방식으로 다시 구분함
- DB Volume 지속성 검증용 SQL을 컨테이너 셸 환경변수와 함께 실행하다 PowerShell 따옴표 충돌로 SQL이 잘림
- 검증 전용 계정을 명시한 단순 명령으로 수정해 테스트 데이터를 생성하고 재시작 후 유지 여부를 확인함
- 처음에는 환경변수 변경 예시를 위해 `.env.example`을 만들었으나 사용자가 현재 값은 민감하지 않고 별도 파일 없이 실행되는 구성을 원함
- Compose에 과제용 기본값을 유지하고 `.env.example`은 제거했으며, `.env`는 포트 변경 시에만 선택적으로 생성하도록 README를 수정함
- 역할별 메인 제목에 Thymeleaf 리터럴 치환 구분자와 같은 `|` 문자를 넣어 템플릿 파싱 500 오류가 발생함
- 리터럴 치환 대신 문자열 결합식으로 제목을 렌더링하도록 수정함
- 역할 미선택 `/main` 요청에서도 `HttpSession`을 새로 만들어 리다이렉트 URL에 세션 ID가 붙고 자동 이동 검증이 실패함
- `request.getSession(false)`로 기존 세션만 조회하고 쿼리 파라미터로 안내하도록 수정해 불필요한 세션 생성을 막음
- AI가 `역할에 따라 메인을 다르게 렌더링`한다는 결정을 역할별로 메인 본문 전체를 교체하는 방식으로 구현함
- 사용자가 원한 구조는 모든 역할이 같은 웹소설 탐색 메인을 사용하고 작가에게 `내 작품`, 관리자에게 `운영·주문 관리`처럼 권한별 메뉴만 추가하는 방식이었음
- 역할은 콘텐츠 접근 화면을 분리하는 기준이 아니라 추가 관리 기능을 노출하는 권한으로 사용하고, 작가·관리자도 독자와 같은 작품 탐색·열람 화면을 이용하도록 수정하기로 함

### 회원·권한 설계 변경

- 초기 판단: 역할 선택마다 체험 회원을 새로 만들고 닉네임에 ID를 붙여 화면에 표시함
- 문제: 로그아웃 후 다시 들어오면 이전 작품 소유자를 이어갈 수 없고, 회원 ID·닉네임은 과제 데모에 불필요함
- 최종 결정: 역할별 고정 체험 회원 1명만 두고 재사용한다. 닉네임은 제거하고 화면에는 역할명만 표시한다. `UNIQUE(member_type)`과 최초 지연 생성으로 맞춘다
- 재발 방지: 회원가입·로그인을 제외해도 소유권 재진입이 필요한지 먼저 확인하고, 고정 회원 vs 매번 생성 중 하나를 문서에 명시한다

- 초기 판단: 세션의 role만으로 CRUD 접근을 구분하면 충분하다고 봄
- 문제: 역할만으로는 누가 작성한 작품인지 식별할 수 없고, 같은 역할이면 모든 작품을 수정하게 됨
- 최종 결정: 세션에 고정 `memberId`와 역할을 함께 저장한다. 역할은 기능 범위, 회원 ID는 소유권 검증에 사용한다
- 재발 방지: 권한과 소유권을 문서·Service에서 항상 분리해 적는다

- 초기 판단: 독자↔작가 빠른 양방향 전환 버튼을 두면 데모 검증이 편하다고 봄
- 문제: 작가는 이미 독자 기능을 포함하므로 되돌릴 필요가 없고, 버튼이 실서비스의 양방향 역할 전환처럼 오해됨
- 최종 결정: 독자→작가 체험만 유지하고 작가→독자 버튼은 제거한다. 독자 화면 재검증은 `역할 변경`(로그아웃) 후 랜딩 재선택으로 한다. 실서비스 작가 전환에는 펀딩 피해 방지를 위한 엄격한 인증이 필요함을 문서에 명시한다
- 재발 방지: 누적 권한 모델에서는 상위 역할의 하위 되돌리기 UI를 기본으로 만들지 않는다

- 초기 판단: 인증 제외를 회원 데이터 자체를 두지 않는 것으로 해석하거나, 반대로 역할 선택마다 회원 가입처럼 생성함
- 문제: 전자는 소유권을 못 잡고, 후자는 인증 없는 회원가입처럼 보임
- 최종 결정: 인증·비밀번호는 구현하지 않고, 역할별 고정 체험 회원으로 소유권만 구분한다. 역할 선택은 보안 인증이 아님을 README와 요구사항에 명시한다
- 재발 방지: “인증 제외”와 “소유자 식별용 최소 회원”을 같은 문장에서 구분해서 적는다

## 주제 확정 기록 (사용자 이해·검증)

- 확정 주제: 완결 조건부 웹소설 소장본 펀딩 서비스
- 결제·환불은 모의 상태만 구현
- 기존 웹소설 플랫폼 연동은 확장안으로만 둠
- 기술 스택: Java 21, Spring Boot 4.1.0, Maven, JPA, MariaDB, Thymeleaf, JavaScript, Bootstrap 5.3.8, Docker Compose
- Docker 실행: 호스트에서 `docker compose up --build`를 실행하고 Maven 빌드·Java 앱·MariaDB는 Docker 내부에서 처리
- DB 연결: 컨테이너 앱은 `db:3306`, IDE에서 실행한 앱은 `localhost:3307` 사용
- 환경변수: Compose 기본값으로 바로 실행하며 `.env`는 포트 변경 시에만 선택적으로 사용
- 데모 회원: 역할별 고정 체험 회원 1명, 세션에 memberId+역할 저장, 닉네임 미사용
- 권한: `독자 < 작가 < 관리자` 누적. 독자→작가 체험만 제공, 작가→독자 되돌리기 없음
- 소유권: 리소스 ID + 세션 회원 ID로 검증. 권한과 소유권 분리
- 현재 상태: Phase 1 + Lv1 선행 화면 + 작품 CRUD·공개 목록·상세 완료, 부·회차 CRUD는 미구현

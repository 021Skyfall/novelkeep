## 1. 서비스 소개

### 어떤 서비스인가

웹소설 **연재·열람**이 본체이고, 부(권) 단위 **소장본 펀딩 → 모의 결제 → 운영자 승인 → 제작 주문**을 부가로 붙인 데모 플랫폼입니다.

### 누구를 위한가

| 역할 | 대상 |
|---|---|
| 주요 | 미완결 걱정 없이 좋아하는 웹소설을 **실물로 소장**하려는 **20~30대 독자** (페르소나 R1~R5). 화면은 **PC 데모 기준** |
| 보조 | 소장본 수요를 확인하고 재고 부담 없이 추가 수익을 원하는 **독립 웹소설 작가** (W1~W5, 주로 PC 집필) |
| 운영 | 펀딩 승인·주문 제작 상태를 관리하는 **운영자** (A1, PC) |

회원가입·로그인은 없고, 랜딩에서 **독자 / 작가 / 운영자** 체험 역할을 고릅니다.

### 주요 기능

- 랜딩에서 체험 역할 선택 (고정 체험 회원 + 세션)
- 작가: 작품·부·회차 작성·수정·공개, 부별 펀딩 시작·수정·마감
- 독자: 작품 탐색·회차 읽기·댓글·책갈피·추천·즐겨찾기
- 독자: 소장본 펀딩 참여(모의 결제)·OPEN 중 환불·내 펀딩·주문 조회
- 작가: 내 펀딩 관리에서 승인·출판 상태 확인
- 운영자: 대시보드, 펀딩 승인·거절, 주문 6단계, CSV/JSON 내보내기

### 과제에서 의도적으로 뺀 것

- 실제 회원가입·로그인, PG 결제·환불, 인쇄 API, 배송
- 웹툰·외부 플랫폼 연동 (확장안만 문서에 기록)

## 2. 실행 방법 (Docker)

Docker와 Docker Compose만 있으면 됩니다. (로컬 Java·Maven·MariaDB 설치 불필요)

```bash
# 저장소 클론
git clone <repo-url>
cd novelkeep

# 실행 (이미지 빌드 포함)
docker compose up --build

# 접속
# http://localhost:8080
```

`docker-compose up --build` 형태도 동일하게 동작합니다.

| 항목 | 설명 |
|---|---|
| 접속 | `http://localhost:8080` |
| 환경변수 | **기본값으로 바로 실행**됩니다. `.env.example` 복사 단계는 **필요 없습니다.** |
| DB | `create-drop` → 앱을 **재시작하면 시드가 다시** 들어갑니다. 세션(역할)도 사라집니다. |

### 시드(데모 데이터) 요약

- 체험 회원 3명 · 작품 50 · 부 132 · 회차 약 1,177
- 추천·즐겨찾기·책갈피 초기값 없음 (직접 토글해 확인)
- mock 독자로 게이지를 채우고, 체험 독자는 참여/주문/환불·참여 가능 OPEN을 가짐
- 탐색 목록 앞쪽 1~2위는 목표가 거의 찬 OPEN(참여·마감 흐름을 짧게 확인하기 위함)

### 포트를 바꿀 때

프로젝트 루트에 `.env`만 만들면 됩니다.

```dotenv
APP_PORT=8081
DB_PORT=3308
```

- `APP_PORT`: 브라우저 접속 포트 → `http://localhost:8081`
- `DB_PORT`: 로컬에서 MariaDB 컨테이너에 붙을 때 쓰는 포트

### 종료·자원 삭제

```bash
docker compose down -v --rmi all --remove-orphans
```

컨테이너, 네트워크, DB Volume, 서비스 이미지를 함께 지웁니다.

## 3. 완성한 레벨

**Lv1 · Lv2 · Lv3까지 모두 구현했습니다.**

### Lv1 — 콘텐츠 서비스

- 랜딩·체험 역할, 공통 메인, 고정 체험 회원·세션
- 작품 CRUD, 공개 탐색 / 내 작품 분리, 작품 상세에서 부·회차 관리
- 회차 작성·수정·열람, 미공개 권은 독자에게 미노출
- 다중 장르(AND 검색), 추천·즐겨찾기·이어읽기 책갈피
- 메인 쇼케이스(인기·신작·완결·펀딩 벨트), 회차 댓글(대댓글 1단·소프트 삭제)
- 공통 상단 탭·다크모드(기본 **다크**)

### Lv2 — 펀딩·주문

- 작품 상세 **부별** 「출판 펀딩 시작」(목표 부수 ≥10)
- OPEN 중: 작성·수정·공개/비공개 **가능**, **삭제만 불가**
- 작가 마감 → SUCCESS(부 완결+목표) / FAILED → **승인 대기**
- 독자 모의 결제 참여·OPEN 환불(펀딩 상세에 잔류)·내 펀딩·주문
- 운영자 펀딩 승인(주문 접수 / 모의 환불)·거절(OPEN 복귀)
- 주문 출판 6단계, 작가·독자 화면에서 상태 조회

### Lv3 — UX·운영

- PC 기준 UI: 빈 목록·오류 안내, AJAX 탐색·필터, sticky 내비·플로팅, 다크모드
- 반응형 레이아웃(화면 너비에 맞춰 줄바꿈·배치) — **모바일 전용 UX는 미작업**
- 카드 메타/장르 분리·인라인 `...`, 펀딩 게이지·배지
- 운영자 대시보드, 주문·펀딩·대시보드 CSV/JSON 내보내기

## 4. 사용자 경험(UI/UX) 설계

이번 UX는 **데스크톱(PC) 화면을 기준**으로 잡았습니다.  
모바일은 Bootstrap 반응형·레이아웃이 줄어드는 수준만 반영했고, 터치 동선·본문 가독성·스티키 위치 등 **모바일 전용 UX는 거의 손보지 않았습니다.** (시간이 더 있었다면 할 일 → [7절](#시간이-더-있다면))

페르소나 원문: [docs/01_사용자_페르소나.md](docs/01_사용자_페르소나.md)

### 타겟을 어떻게 잡았나

페르소나를 역할별로 묶어, **누가·무엇을 하고 싶은지**를 화면 우선순위로 옮겼습니다.

| 역할 | 대표 페르소나 | 상황·니즈 | 화면에서 맞춘 점 |
|---|---|---|---|
| 독자 | R1 윤지아(신중), R3 오세진(예산), R4 한예린(완결 몰아보기), R5 임태경(후원) | 20~30대. 미완결 결제 경험이 있거나, 금액·환불이 분명해야 참여함. 완결작만 모아서 보고 싶거나 진행률이 보여야 안심함 | 완결·펀딩 상태·환불 조건을 쉬운 한국어로. 탐색 필터·내 펀딩·주문 탭으로 상태를 구분 |
| 독자→작가 | R6 서나래 | 독자로 쓰다 첫 연재를 시작하고 싶음. 계정·화면이 갈라지면 부담 | 랜딩의 작가 체험·「작가가 되고 싶으신가요?」안내. 작가는 독자 메뉴를 누적 |
| 작가 | W1 김하린(신인), W2 박도윤(독립), W3 이수민(다부), W4 최우진(완결작), W5 정서윤(필명) | 대부분 **PC에서 집필·관리**. 조회 수만으로는 수요를 모름. 재고·배송 없이 소장본을 주고 싶음. 부마다 출판하고 싶거나 필명만 노출하고 싶음 | 작품 상세에서 부·회차·펀딩을 한곳에서. 게이지·승인/출판 상태. 필명 중심 표시 |
| 운영 | A1 이지훈 | **PC**에서 매일 승인·주문 진전·누락 여부를 확인 | `/admin` 대시보드 → 펀딩 승인 → 주문 묶음·6단계·CSV/JSON |

기기 기준은 **PC 우선**입니다. 좁은 화면에서도 깨지지 않게 반응형만 적용했고, 모바일 전용 패턴(하단 탭, 본문 타이포 튜닝 등)은 넣지 않았습니다.

### 화면·흐름에서 내린 판단

**진입·역할**

- 공개 작품도 **랜딩에서 역할을 고른 뒤에만** 들어가게 했습니다. 역할 없이 둘러보기만 두면, 심사·데모에서 “누구 소유의 무엇을 보는지”가 흐려지기 때문입니다.
- 역할마다 **고정 체험 회원 1명**을 세션에 붙입니다. 같은 역할로 다시 들어와도 작품·참여·주문이 이어져, 가입 없이도 소유권을 반복 확인할 수 있습니다.
- 역할 선택은 **보안 로그인이 아닙니다.** 메뉴 범위(역할)와 데이터 소유(memberId)를 나누기 위한 데모 장치입니다.

**메뉴·홈**

- 웹소설 **탐색이 본체**이므로 독자·작가는 **같은 `/main`·같은 탐색 원본**을 씁니다. 역할마다 다른 홈을 만들면 관리 도구처럼 보이기 쉽습니다.
- 작가만 **내 작품·내 펀딩** 메뉴를 추가합니다. 운영자는 **대시보드·펀딩·주문**만 두고 독자·작가 누적 메뉴는 붙이지 않습니다. (공개 URL 직접 열람은 허용)
- 작가는 독자 기능을 포함하므로 **작가→독자 되돌리기**는 없습니다. 독자 화면을 다시 보려면 **역할 변경** 후 랜딩에서 독자를 고릅니다.
- 독자→작가 체험은 **다른 고정 회원**으로 바뀌므로 즐겨찾기·추천이 이어지지 않습니다. R6 시나리오는 “진입 느낌”만 보여주고, 데이터 연속성은 실서비스의 권한 승격으로 남겨 두었습니다.

**콘텐츠·상태 표현**

- **부 1개 = 소장본 1권.** 단권은 내부 `본편`을 숨기고 회차만 보여, “부/권” 용어 부담을 줄였습니다.
- 연재 상태와 공개 여부를 분리합니다. 회차를 비공개로 바꿔도 **부 완결이 자동으로 풀리지 않게** 해, W3처럼 부 단위로 관리하는 작가가 상태를 직접 통제하게 했습니다.
- 내부 코드 대신 `연재 중`, `1부 완결`, `펀딩 중`, `접수`, `배송중`처럼 **한국어 상태**를 씁니다. R1·R3처럼 조건을 먼저 확인하는 독자를 의식했습니다.
- 빈 목록·권한 부족·잘못된 상태 변경에는 **다음 행동**(역할 선택, 작품 둘러보기 등)을 안내합니다.

**펀딩·주문 동선**

- 펀딩 **시작은 작품 상세의 부별 버튼**, 목록·수정·마감은 **내 펀딩 관리**로 나눴습니다. 개설 맥락(어느 부인지)과 운영 목록을 분리하기 위해서입니다.
- OPEN 중에는 **삭제만 막고** 작성·수정·공개/비공개는 허용합니다. 연재 중 펀딩을 열어 둔 작가(W1·W3)가 내용을 고칠 수 있게 하되, 캠페인에 묶인 부를 통째로 지우지 못하게 했습니다.
- 독자 환불은 **펀딩 상세에서만**, 환불 후에도 **같은 상세에 남아** 게이지·버튼을 바로 확인하게 했습니다. “내 펀딩 목록으로 튕기면” 결과가 안 보이는 느낌을 줄이려는 판단입니다.
- 마감 SUCCESS/FAILED 후 **운영자 승인**이 있어야 주문·일괄 환불이 됩니다. 작가 혼자 상태를 끝내지 않고, A1 운영 흐름을 데모에 남기기 위해서입니다.

**탐색·상호작용 (PC 기준)**

- 추천·즐겨찾기·검색·필터는 **AJAX 부분 갱신**으로 스크롤·위치를 유지합니다. JS 실패 시에는 전체 새로고침으로 동작합니다.
- 메인 벨트는 클릭과 가로 드래그를 같이 쓰되, 링크 네이티브 드래그와 구분하는 임계값을 두었습니다.
- 다크 모드를 기본으로 두고 선택은 `localStorage`에 저장합니다.

### 의도적으로 넣지 않은 것

| 항목 | 왜 뺐는지 |
|---|---|
| 실제 회원가입·로그인·비밀번호 | 과제에서 인증을 빼고 **연재→펀딩→주문** 흐름을 보이게 하기 위함입니다. 대신 역할별 고정 체험 회원으로 소유권만 구분합니다. |
| 실제 PG 결제·환불·정산 | 금액·상태 전이(참여→환불→주문)만 검증하면 충분하다고 봤습니다. 실연동은 키·정산·보안 범위가 커져 Lv2 핵심을 가립니다. |
| 실제 인쇄 API·PDF 조판·배송 | 스위트북 연동은 **확장 스토리**로 두고, 데모에서는 “승인되면 제작 6단계가 진행된다”는 운영 화면까지로 끊었습니다. |
| 모바일 전용 UX (하단 탭, 본문 타이포·제스처 최적화 등) | 일정 안에서 **PC 데모·역할 동선**을 우선했습니다. 반응형으로 레이아웃만 줄어들게 했고, 모바일 사용성 튜닝은 다음 과제로 남겼습니다. |
| 좋아요·서버 푸시 알림·고급 검색 | 추천·즐겨찾기·장르 AND 검색으로 탐색 최소 요건은 충족한다고 봤습니다. 푸시·고도 검색은 본체 동선이 아닙니다. |
| 작가→독자 되돌리기 버튼 | 작가가 독자 메뉴를 이미 포함합니다. 되돌리기를 두면 “별도 독자 계정”처럼 오해되기 쉽습니다. 독자 검증은 **역할 변경**으로 합니다. |
| 작품당 동시 OPEN 상한 | 부당 OPEN=1과 홈 노출 상한으로 충분하다고 판단해, 작품당 상한은 두지 않았습니다. |

## 5. 기술 스택 및 아키텍처

### 스택

| 구분 | 선택 |
|---|---|
| Backend | Java 21, Spring Boot 4.1.0, Spring Data JPA |
| Frontend | Thymeleaf, JavaScript, Bootstrap 5.3.8 |
| DB | MariaDB 11.8.8 LTS |
| Build / Run | Maven 3.9.16, Docker Compose |

### 왜 이 스택인가

| 기술 | 이유 |
|---|---|
| Java 21 | LTS와 최신성의 균형 |
| Spring Boot 4.1 | Java 21을 지원하는 신규 프로젝트용 안정판 |
| JPA | 작품·회차·펀딩·주문 연관 CRUD를 빠르게 |
| MariaDB | 익숙함 + 공식 Docker 이미지로 재현 쉬움 |
| Thymeleaf | 프론트 빌드 없이 폼·목록 중심 화면 |
| Bootstrap | 반응형 UI를 기성 컴포넌트로 |
| Docker Compose | 심사자가 로컬 JDK 없이 동일 환경 실행 |

### 아키텍처

```mermaid
flowchart LR
    U["브라우저"] --> A["Spring Boot 앱"]
    A --> C["Controller"]
    C --> S["Service"]
    S --> R["JPA Repository"]
    R --> D["MariaDB"]
```

- 패키지: `com.novelkeep.{도메인}.{계층}` (`home`, `member`, `novel`, `funding`, `order`, `admin`)
- 컨테이너 안 DB: `db:3306` / 호스트 IDE: `localhost:3307`
- DB healthcheck 후 앱 기동, `DemoDataInitializer`로 시드 적재

## 6. AI 도구 사용 내역

| 서브 에이전트 | `explore`: 코드·문서 현황 조사 / `cursor-guide`: IDE·미리보기 설정 확인 / `generalPurpose`: 일부 보조 작업 |

## 7. 설계 의도

### 왜 이 아이디어인가

- 웹소설은 **인쇄 없이도** 소비되는 콘텐츠라, “콘텐츠가 본체”라는 과제 조건에 맞습니다.
- **완결·목표 조건부 펀딩**으로 독자의 미완결 결제 위험을 줄이고, 작가에게는 완결 동기를 줍니다.
- 연재 흐름을 종이책 주문으로 자연스럽게 이을 수 있습니다.

### 사업적으로 어떻게 보나

- 스위트북 Book Print API를 붙일 **웹소설 플랫폼형 B2B 파트너** 사례로 설명하기 좋습니다.
- 사전 펀딩으로 실수요를 확인하면 작가·플랫폼의 **재고 위험**을 줄일 수 있습니다.
- 소규모 팬덤 독립 작가에게 추가 수익·소장본 제작 창구가 됩니다.

### 데모 권한 설계

- 인증을 뺀 이유: 콘텐츠·펀딩·주문 **핵심 흐름 검증**에 집중하기 위함입니다.
- 역할별 고정 체험 회원: 가입 없이 소유권을 반복 확인하고, 같은 역할로 다시 들어와도 데이터를 이어 보기 위함입니다.
- 역할 선택은 **보안 인증이 아닙니다.** 실서비스에는 별도 인증·인가가 필요합니다.

### 시간이 더 있다면

- **모바일 최적화** — 회차 본문 타이포·여백, 터치 동선, 스티키/고정 버튼 위치, 좁은 폭에서의 표·필터 UX
- 외부 웹소설 플랫폼 연동, 실결제·인쇄 API, 표지·판형·미리보기
- 알림·커뮤니티 강화, 작가 정산·배송 추적, 실서비스용 작가 전환 인증

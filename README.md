## 1. 서비스 소개

### 어떤 서비스인가

웹소설 **연재·열람**이 본체이고, 부(권) 단위 **소장본 펀딩 → 모의 결제 → 운영자 승인 → 제작 주문**을 이어 주는 플랫폼입니다.

### 누구를 위한 서비스인가

| 역할 | 대상 |
|---|---|
| 주요 | 미완결 걱정 없이 좋아하는 웹소설을 **실물로 소장**하려는 **20~30대 독자** (페르소나 R1~R5). 화면은 **PC 기준** |
| 보조 | 소장본 수요를 확인하고 재고 부담 없이 추가 수익을 원하는 **독립 웹소설 작가** (W1~W5, 주로 PC 집필) |
| 운영 | 펀딩 승인·주문 제작 상태를 관리하는 **운영자** (A1, PC) |

회원가입·로그인은 없으며, 첫 화면(랜딩)에서 **독자 / 작가 / 운영자** 역할을 고른 뒤 서비스를 이용합니다.

### 주요 기능

**독자**

- 메인에서 인기·신작·완결·진행 중 펀딩 둘러보기
- 작품 탐색·필터, 추천·즐겨찾기, 회차 읽기·책갈피
- 내 댓글 관리(작성·수정·삭제·답글)
- 소장본 펀딩 참여(모의 결제), 펀딩 중 환불, 내 펀딩·주문 조회

**작가**

- 내 작품·부·회차 작성·수정·공개/비공개
- 부별 출판 펀딩 시작·수정·마감, 내 펀딩 관리
- 펀딩 중에도 회차 작성·수정·공개 가능(해당 부·회차 **삭제만** 불가)
- 승인·출판 상태 확인 (독자 기능 포함)

**운영자**

- 대시보드에서 핵심 지표 확인
- 펀딩 승인·거절, 주문 제작 6단계 진전
- 주문·펀딩·대시보드 CSV/JSON 내보내기

## 2. 실행 방법 (Docker)

Docker Desktop(또는 동등한 Docker 엔진)이 **실행 중**이어야 하고, **Docker Compose**가 설치되어 있어야 합니다.  
로컬에 Java·Maven·MariaDB를 따로 둘 필요는 없습니다.

내장 데모 데이터 양이 있어, PC 성능에 따라 **첫 기동·이미지 빌드에 수 분**이 걸릴 수 있습니다. 앱 로그에 기동 완료가 보이면 `http://localhost:8080`으로 접속하면 됩니다.

```bash
# 저장소 클론
git clone https://github.com/021Skyfall/novelkeep.git
cd novelkeep

# 실행 (이미지 빌드 포함)
docker compose up --build

# 접속
# http://localhost:8080
```

`--build`는 앱 이미지를 **현재 소스 기준으로 다시 빌드**한 뒤 띄우기 위해 사용합니다. 코드·의존성이 바뀐 뒤에도 같은 명령으로 최신 상태를 맞출 수 있습니다.

| 항목 | 설명 |
|---|---|
| 접속 | `http://localhost:8080` |
| DB | `create-drop` → 앱을 **재시작하면 데이터가 다시** 들어갑니다. |

### 데모 데이터 요약

- 체험 회원 3명 · 작품 50 · 부 132 · 회차 약 1,177
- 추천·즐겨찾기·책갈피 초기값 없음 (직접 토글해 확인)
- 체험 독자는 참여/주문/환불·참여 가능한 펀딩을 가짐
- 작품 탐색 목록 **첫 번째·두 번째**는 거의 찬 펀딩(참여·마감 흐름을 짧게 확인하기 위함)

### 포트를 바꿀 때

기본은 **8080**만 열면 됩니다. 포트가 겹칠 때만 프로젝트 루트에 `.env`를 만듭니다.

```dotenv
APP_PORT=8081
DB_PORT=3308
```

- `APP_PORT`: 브라우저 접속 포트 (`http://localhost:8081`)
- `DB_PORT`: 호스트에서 MariaDB 컨테이너에 붙을 때 쓰는 포트

### 종료 및 자원 삭제

```bash
docker compose down -v --rmi all --remove-orphans
```

컨테이너, 네트워크, DB Volume, 서비스 이미지를 함께 지웁니다.

## 3. 완성한 레벨

**Lv1 · Lv2 · Lv3까지 모두 구현했습니다.** (접속해서 쓸 수 있는 기능 기준)

### Lv1 — 콘텐츠 서비스

- 랜딩에서 독자·작가·운영자 역할 선택 후 서비스 진입
- 공통 메인: 인기작·새 회차·완결·진행 중 펀딩 벨트(클릭·가로 드래그)
- 작품 탐색: 제목·장르(여러 개 AND)·펀딩 중 여부 필터, 추천·즐겨찾기
- 작품 상세·회차 읽기, 이전화/다음화, 책갈피·내 책갈피
- 작가: 내 작품 등록·수정, 부·회차 관리, 공개/비공개, 일괄 공개·비공개·삭제
- 미공개 작품·부·회차는 독자에게 보이지 않음
- 회차 댓글·답글(1단), 본인 수정·소프트 삭제
- 상단 메뉴·다크/라이트 테마(기본 다크), 맨 위·홈 플로팅 버튼

### Lv2 — 펀딩·주문

- 작가: 작품 상세에서 부별 「출판 펀딩 시작」(목표 부수 10 이상)
- 펀딩 중: 회차 작성·수정·공개/비공개 가능, **삭제만 불가**
- 작가: 내 펀딩 관리에서 수정·취소(수요 0만)·마감
- 마감 결과: 성공(부 완결+목표 달성) / 실패 → 운영자 승인 대기
- 독자: 펀딩 상세에서 모의 결제로 참여, 펀딩 중 환불(같은 상세에 남아 게이지 확인)
- 독자: 내 펀딩·주문(전체 / 참여 중 / 주문 / 환불 탭, 영수증 보기)
- 운영자: 펀딩 승인(주문 접수 또는 모의 환불)·거절(다시 펀딩 중으로)
- 운영자: 주문 제작 상태 6단계 진전, 작가·독자 화면에서 상태 확인

### Lv3 — UX·운영

- 목록·검색·필터·추천·즐겨찾기의 **부분 화면 갱신(AJAX)** 으로 스크롤 유지
- 카드 메타/장르 분리, 장르 `...` 펼침, 펀딩 게이지·배지
- 빈 목록·오류 시 다음 행동 안내, sticky 상단 메뉴
- 반응형 레이아웃(너비에 맞춰 줄바꿈) — **모바일 전용 UX는 미작업**
- 운영자 대시보드, 주문·펀딩·대시보드 CSV/JSON 내보내기
- 일자 범위 검색(flatpickr) 등 운영·독자 목록 UX

## 4. 사용자 경험(UI/UX) 설계

이번 UX는 **데스크톱(PC) 화면을 기준**으로 잡았습니다.  
모바일은 Bootstrap 반응형으로 레이아웃만 줄어들게 했고, 터치 동선·본문 가독성·고정 버튼 위치 등 **모바일 전용 UX는 거의 손보지 않았습니다.** (시간이 더 있었다면 → [7절](#시간이-더-있다면))

페르소나 원문: [docs/01_사용자_페르소나.md](docs/01_사용자_페르소나.md)

### 타겟을 어떻게 잡았나

독자·작가·운영자가 **실제로 무엇을 하려는지**를 화면 우선순위로 옮겼습니다.

| 역할 | 대표 페르소나 | 상황·니즈 | 화면에서 맞춘 점 |
|---|---|---|---|
| 독자 | R1 윤지아(신중), R3 오세진(예산), R4 한예린(완결 몰아보기), R5 임태경(후원) | 미완결 결제 경험이 있거나 금액·환불이 분명해야 함. 완결작·진행률이 보여야 안심 | 완결·펀딩 중·환불 조건을 한국어로. 탐색 필터·내 펀딩·주문 탭으로 상태 구분 |
| 독자→작가 | R6 서나래 | 독자로 쓰다 연재를 시작하고 싶음. 화면이 갈라지면 부담 | 「작가가 되고 싶으신가요?」안내. 작가는 독자 메뉴를 그대로 씀 |
| 작가 | W1 김하린(신인), W2 박도윤(독립), W3 이수민(여러 부 연재), W4 최우진(완결작), W5 정서윤(필명) | PC에서 집필·관리. 조회 수만으로는 수요를 모름. 부마다 출판하거나 필명만 노출하고 싶음 | 작품 상세에서 부·회차·펀딩을 한곳에서. 게이지·승인/출판 상태. 필명 중심 표시 |
| 운영 | A1 이지훈 | PC에서 승인·주문 진전·누락 여부를 확인 | 대시보드 → 펀딩 승인 → 주문 묶음·6단계·CSV/JSON |

### 화면·흐름에서 내린 판단

**진입**

- 회원 인증(회원가입·로그인)이 없어, 첫 진입은 **랜딩에서 역할만 고른 뒤** 본 서비스로 들어가게 했습니다.
- 역할마다 고정 체험 계정을 두어, 같은 역할로 다시 들어와도 작품·참여·주문이 이어지게 했습니다.

**메뉴·홈**

- 웹소설 **탐색이 본체**이므로 독자·작가는 같은 메인·같은 탐색을 씁니다. 역할마다 다른 홈을 두면 관리 도구처럼 보이기 쉽습니다.
- 작가만 **내 작품·내 펀딩**을 추가하고, 운영자는 **대시보드·펀딩·주문**만 둡니다. (공개 URL로 작품 탐색은 가능)
- 작가는 독자 기능을 포함하므로 **작가→독자 되돌리기**는 없습니다. 독자 화면을 다시 보려면 **역할 변경** 후 랜딩에서 독자를 고릅니다.

**콘텐츠·상태**

- **부 1개 = 소장본 1권.** 단권은 내부 `본편`을 숨기고 회차만 보여, 용어 부담을 줄였습니다.
- 연재 상태와 공개 여부를 분리합니다. 회차만 비공개로 바꿔도 부 완결이 자동으로 풀리지 않아, 여러 부를 연재하는 작가가 상태를 직접 통제할 수 있습니다.
- `연재 중`, `1부 완결`, `펀딩 중`, `접수`, `배송중`처럼 **쉬운 한국어 상태**를 씁니다.
- 빈 목록·권한 부족·잘못된 상태 변경에는 **다음에 할 일**을 안내합니다.

**펀딩·주문**

- 펀딩 **시작은 작품 상세의 부별 버튼**, 목록·수정·마감은 **내 펀딩 관리**로 나눴습니다. “어느 부에 여는지”와 “진행 중인 펀딩을 모아 보는 것”을 분리하기 위해서입니다.
- 펀딩 중에는 **삭제만 막고** 작성·수정·공개/비공개는 허용합니다. 연재하면서 펀딩을 연 작가가 내용을 고칠 수 있게 하되, 캠페인에 묶인 부를 통째로 지우지 못하게 했습니다.
- 독자 환불은 **펀딩 상세에서만** 하고, 환불 후에도 **같은 화면에 남아** 게이지와 버튼이 바로 바뀌게 했습니다.
- 마감(성공/실패) 후 **운영자 승인**이 있어야 주문·일괄 환불이 됩니다. 작가 혼자 끝내지 않고 **운영 흐름**을 남기기 위해서입니다.

**탐색·실시간 갱신 (PC)**

- 추천·즐겨찾기·검색·필터·내 펀딩·운영자 목록은 **AJAX로 목록만 다시 그려** 스크롤·필터 상태를 유지합니다. 페이지 전체가 깜빡이지 않아 “눌러 보고 바로 결과 확인”이 쉽습니다.
- JS가 실패해도 일반 폼 제출·전체 새로고침으로 같은 기능을 쓸 수 있게 했습니다.
- 메인 벨트는 클릭과 가로 드래그를 같이 쓰고, 미세 움직임은 클릭으로 처리해 링크와 드래그가 서로 가로채지 않게 했습니다.
- 다크 모드를 기본으로 두고, 선택은 브라우저에 저장합니다.

### 의도적으로 넣지 않은 것

| 항목 | 왜 뺐는지 |
|---|---|
| 모바일 전용 UX (하단 탭, 본문 타이포·제스처 최적화 등) | PC·역할 동선을 우선했습니다. 반응형으로 레이아웃만 줄였고, 모바일 사용성 튜닝은 다음으로 남겼습니다. |
| 좋아요·서버 푸시 알림·고급 검색 | 추천·즐겨찾기·장르 AND 검색으로 탐색 최소 요건은 충족한다고 봤습니다. |
| 작가→독자 되돌리기 버튼 | 작가가 독자 메뉴를 이미 포함합니다. 되돌리기를 두면 별도 독자 계정처럼 오해되기 쉽습니다. |
| 작품당 동시 펀딩 상한 | 부마다 진행 중 펀딩은 1개, 홈 노출 상한으로 충분하다고 판단해 작품당 상한은 두지 않았습니다. |
| 웹툰·외부 연재 플랫폼 연동 | 이번 범위의 본체는 자사 연재·펀딩·주문 흐름입니다. 확장은 문서로만 남겼습니다. |
| 실시간 채팅·커뮤니티·작가 정산 화면 | 소장본 펀딩·주문 전환이 핵심이라, 부가 커뮤니티·정산은 넣지 않았습니다. |

### 주요 화면 캡처

역할별 핵심 화면을 **사용 흐름 순**으로 정리했습니다. Docker로 실행한 뒤 같은 경로에서 확인할 수 있습니다.

#### 1) 랜딩 — 역할 선택 (`/`)

서비스 소개와 함께 독자·작가·운영자를 고르는 첫 화면입니다.

![02 독자 메인](docs/images/02-main.png)

제목·장르·펀딩 중 여부로 작품을 찾고, 추천·즐겨찾기를 토글할 수 있습니다.

![04 작품 상세(독자)](docs/images/04-novel-detail-reader.png)

![05 회차 읽기](docs/images/05-episode-read.png)

#### 6) 펀딩 상세 — 참여·게이지 (`/fundings/{id}`)

![06 펀딩 상세](docs/images/06-funding-detail.png)

#### 7) 내 펀딩·주문 (`/reader/activities`)

참여 중·주문·환불 내역을 탭으로 구분해 조회합니다.

![07 내 펀딩·주문](docs/images/07-reader-activities.png)

## 5. 기술 스택 및 아키텍처

### 스택

| 구분 | 선택 |
|---|---|
| Backend | Java 21, Spring Boot 4.1.0, Spring Data JPA |
| Frontend | Thymeleaf, JavaScript, Bootstrap 5.3.8 |
| DB | MariaDB 11.8.8 LTS |
| Build / Run | Maven 3.9.16, Docker Compose |

### 왜 이 스택인가

| 기술 | 이유 |
|---|---|
| Java 21 | LTS로 운영 사례가 쌓여 있고, 신규 단독 앱이라 구버전 호환 부담이 없습니다. Java 17보다 최신이면서 Java 25보다 검증 기간이 길어 균형을 맞췄습니다. |
| Spring Boot 4.1 | Java 21을 공식 지원하는 안정판입니다. MVC·JPA·Thymeleaf Starter와 내장 Tomcat으로 WAS·의존성 맞추는 시간을 줄이고 콘텐츠·펀딩 로직에 집중했습니다. |
| Spring Data JPA | 작품·부·회차·펀딩·주문처럼 연관 CRUD가 많아 Repository·연관 매핑이 빠릅니다. 완결·목표 판단은 Service에서 처리합니다. |
| MariaDB | 사용 경험이 있고 공식 Docker 이미지로 환경을 고정하기 쉽습니다. 펀딩·주문 상태처럼 영속 데이터와 제약을 실제 DB로 검증하기 좋습니다. |
| Thymeleaf | 목록·상세·폼 중심이라 SPA·Node 빌드 없이 Controller→화면 전달만으로 충분합니다. 앱 JAR에 템플릿이 포함됩니다. |
| Bootstrap 5.3.8 | 과제에서 기성 UI를 권장합니다. 카드·폼·배지·진행률로 제작 시간을 줄이고 Grid로 반응형만 맞췄습니다. |
| Docker Compose | 심사 환경에서 로컬 JDK 없이 앱·DB를 같은 구성으로 띄우기 위해서입니다. |

### 아키텍처

```mermaid
flowchart LR
    U["브라우저"] --> A["Spring Boot 앱 컨테이너"]
    A --> C["Controller"]
    C --> S["Service"]
    S --> R["JPA Repository"]
    R --> D["MariaDB 컨테이너"]
```

- 요청은 Controller → Service → Repository 순으로만 내려갑니다. 화면용 데이터 조립·권한·소유권 검증은 Service에 둡니다.
- 앱 컨테이너는 Compose의 `db` 호스트(`db:3306`)로 붙고, 호스트 IDE에서 DB만 볼 때는 `localhost:3307`을 씁니다.
- DB healthcheck가 통과한 뒤에 앱이 기동하고, 기동 시 `DemoDataInitializer`가 **데모 데이터를 적재**합니다.
- `ddl-auto: create-drop`이라 앱을 다시 올리면 스키마와 데모 데이터가 처음부터 다시 만들어집니다.

### 패키지 구조

도메인별로 나누고, 각 도메인 안에서 `controller` / `service` / `domain` / `repository` / `dto`를 둡니다.

```text
com.novelkeep
├── home          # 랜딩·메인·역할 세션·데모 데이터·공통 예외/웹 설정
├── member        # 체험 회원(역할별 고정 1명)
├── novel         # 작품·부·회차·장르·추천·즐겨찾기·책갈피·댓글
├── funding       # 펀딩 캠페인·참여·독자 내 활동·작가 펀딩 관리
├── order         # 제작 주문·상태 전이
├── admin         # 운영자 대시보드·주문/펀딩 화면·내보내기
└── common        # 공통 유틸·지원 코드
```

| 패키지 | 담당 |
|---|---|
| `home` | `/`, `/main`, 역할 선택, 쇼케이스, `DemoDataInitializer` |
| `member` | 역할별 고정 회원 조회·생성 |
| `novel` | `/novels`, `/writer/novels`, 부·회차, 탐색 Specification |
| `funding` | `/fundings`, `/reader/activities`, `/writer/publishing` |
| `order` | 주문 엔티티·상태·묶음 조회 |
| `admin` | `/admin`, `/admin/orders`, `/admin/fundings`, CSV/JSON |

## 7. 설계 의도

### 왜 이 아이디어인가

- 웹소설은 **인쇄 없이도** 소비되는 콘텐츠라, “콘텐츠가 본체”라는 과제 조건에 맞습니다. 연재·열람을 중심에 두고, 그 위에 소장본 전환을 얹는 구조로 잡았습니다.
- 독자 입장에서는 **미완결 작품을 미리 결제했다가 연재가 끊기는 경험**이 큽니다. 부 완결·목표 부수 조건을 건 펀딩으로 “조건을 채워야 책이 나온다”는 신뢰를 만들려 했습니다.
- 작가 입장에서는 조회 수만으로는 소장본 수요를 알기 어렵고, 선인쇄·재고 부담이 큽니다. **사전 펀딩으로 수요를 확인한 뒤** 제작 주문으로 넘기는 흐름이 현실적인 동기라고 봤습니다.
- 연재(읽기) → 부 단위 펀딩 → 승인 → 제작 상태 조회까지가 한 제품 안에서 이어지면, 별도 인쇄 업체·스프레드시트로 끊기지 않습니다.

### 사업적으로 어떻게 보나

- 스위트북 Book Print API를 붙일 **웹소설 플랫폼형 B2B 파트너** 사례로 설명하기 좋습니다. 플랫폼이 연재·수요 확인을 하고, 인쇄·물류는 전문 API에 맡기는 역할 분담입니다.
- 사전 펀딩으로 실수요를 확인하면 작가·플랫폼의 **재고·선투입 위험**을 줄일 수 있습니다. 실패 시 모의 환불 상태까지 보여 실패 경로도 제품에 포함됩니다.
- 소규모 팬덤을 가진 독립 작가에게는, 대형 출판 계약 없이도 **팬 대상 소장본**을 제안하는 추가 수익 창구가 됩니다.
- 운영자(승인·주문 6단계·내보내기)를 둔 이유는, B2B로 넘기기 전에 **플랫폼 측에서 검수·제작 진행을 추적**하는 화면이 필요하다는 판단입니다.

### 시간이 더 있다면

- **모바일 최적화** — 회차 본문 타이포·여백, 터치 동선, 스티키/고정 버튼 위치, 좁은 폭에서의 표·필터 UX
- 외부 웹소설 플랫폼 연동, 실결제·인쇄 API, 표지·판형·미리보기
- 알림·커뮤니티 강화, 작가 정산·배송 추적, 실서비스용 작가 전환 인증

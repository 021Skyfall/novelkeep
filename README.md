# 노벨킵 (NovelKeep)

웹소설을 연재·열람하고, 완결·분량·수량 조건을 충족한 작품을 소장본 펀딩과 제작 주문으로 연결하는 플랫폼입니다.

## 현재 상태

- Phase 1: Maven 골조와 Docker·MariaDB 실행 환경 구성 완료
- Lv1 완료: 랜딩·역할 선택, 고정 체험 회원·세션, 공통 메인, 작품·부·회차 CRUD·열람
- Lv1 완료: 공개 탐색/내 작품 분리, 추천·즐겨찾기·완결 필터, AJAX 탐색, 다중 장르 AND, 이어읽기 책갈피
- Lv1 완료: 메인 쇼케이스(인기·신작·완결 각 10, 진행 펀딩 5)·홈 상단 탭·회차 댓글(대댓글 1단·소프트 삭제)
- **독자·작가 Lv1 완료.** 미공개 권 독자 미노출, 작품 상세 권·회차 관리. 회차 공개 전환은 부 완결을 자동 변경하지 않음.
- **Lv2 대부분:** 작가 OPEN·마감(성공/실패 판정) → **운영자 승인** 후 주문 접수/모의 환불, 독자 모의 결제 참여
- **운영자:** `/admin` 대시보드 + `/admin/orders`(캠페인 묶음·상세·영수증·6단계·CSV/JSON) + `/admin/fundings`(승인·거절·CSV/JSON)
- **작가 내 펀딩 관리**(`/writer/publishing`): OPEN/SUCCESS/FAILED·출판 상태 필터, 승인·주문 단계 안내
- **독자 내 펀딩·주문**(`/reader/activities`): 전체/참여 중/주문/환불 탭·테이블. 환불은 펀딩 상세
- 수동 검증: [역할별 테스트 루트](docs/06_역할별_테스트_루트.md)
- **진행률 100%** (Phase1 · Lv1 · Lv2 · Lv3 과제 범위 완료)
- **다음: 최종 스모크 검증**
## 1. 서비스 소개

### 타겟 사용자

- 주요 사용자: 미완결 위험 없이 좋아하는 웹소설을 실물로 소장하려는 20~30대 독자
- 보조 사용자: 소장본 수요를 확인하고 완결 후 추가 수익을 얻으려는 독립 웹소설 작가
- 운영 사용자: 전체 주문과 제작 상태를 관리하는 운영자(체험 역할명 `ADMIN`)

### 주요 기능

- 작가의 작품·부·회차 생성, 조회, 수정과 공개
- 독자의 작품 탐색과 웹소설 회차 열람
- 출판할 연속 회차 범위와 목표 글자 수를 이용한 권별 예상 분량 계산
- 소장본 펀딩 참여와 모의 결제·환불
- 완결·예상 분량·목표 수량을 모두 충족한 펀딩의 책 주문 전환
- 독자·작가의 펀딩 및 주문 상태 조회
- 관리자의 주문 상태 관리, 운영 통계와 CSV·JSON 내보내기
- 랜딩페이지에서 독자·작가·운영자 체험 역할 선택

### 구현 범위

- 콘텐츠 연재와 열람을 본체로 두고 책 제작 주문은 부가 기능으로 구현
- 회원가입·로그인 인증은 구현하지 않고, 역할별 고정 체험 회원과 세션으로 역할·소유권을 구분
- 실제 인쇄 API, PG 결제·환불, 배송은 구현하지 않음
- 웹툰과 외부 웹소설 플랫폼 연동은 향후 확장안으로만 둠

## 2. 실행 방법 (Docker)

Docker와 Docker Compose만 설치되어 있으면 별도 Java·Maven·MariaDB 설치 없이 실행할 수 있습니다.

```bash
git clone <repo-url>
cd novelkeep
docker compose up --build
```

- 접속: `http://localhost:8080`
- 안내문의 기존 명령인 `docker-compose up --build`도 사용 가능
- `docker-compose.yml`에 환경변수 기본값이 있어 별도 `.env` 파일은 필요하지 않음
- 개발·데모 DB는 `create-drop`을 사용하므로 앱을 재시작하면 기존 데이터가 삭제되고 현재 구현 범위의 목 데이터가 다시 생성됨
- 자동 생성 데이터: 역할별 체험 회원 3명, 작품 50건, 부 132건, 회차 1,177건(작품당 20~27화), 추천 0건
- 펀딩 참여·주문·환불 시드는 **mock 독자**로 게이지·다인 참여를 채운다. **체험 독자**는 참여 중·주문·환불 + 참여 가능 OPEN을 갖고, 탐색 1–2위는 목표 달성 OPEN으로 핀한다.
- 완결작은 모두 3개 부(3권)와 공개 완료 회차로 구성하고, 연재작은 완결 부→연재 부→집필 중 부 순서를 유지
- 각 부는 소장본 1권의 출판 단위이며, 목 데이터의 다중 부는 부당 7~9화를 가지도록 구성
- 공개·미공개 작품은 작가와 관리자 소유로 분산
- 장르는 소설 분야 50종을 공통 `NovelGenre` enum으로 관리하며 작품당 1~8개(`novel_genre`)를 저장한다. 목 데이터는 작품당 2~8개(일부는 긴 이름 7~8개)로 넣어 장르 줄 인라인 `...` 펼침을 확인한다. 검색은 선택 장르 AND다. 탐색·내 작품에는 **펀딩 중 Y/N** 필터가 있다.
- 이어읽기 책갈피는 회원·작품별 1개이며 초기 시드는 넣지 않는다. 회차 읽기에서 저장하고 작품 상세 또는 `내 책갈피` 메뉴에서 이어 읽기·해제한다.
- 내 즐겨찾기는 사용자 토글 동작 확인을 위해 초기 데이터를 넣지 않음

### 포트 변경

포트를 변경할 때만 프로젝트 루트에 `.env` 파일을 만들고 아래처럼 작성합니다.

```dotenv
APP_PORT=8081
DB_PORT=3308
```

- `APP_PORT`: 웹 접속 포트
- `DB_PORT`: 로컬 개발 도구에서 MariaDB 컨테이너에 접근할 때 사용하는 포트
- 위 설정의 웹 접속 주소: `http://localhost:8081`

### 종료 및 노벨킵 Docker 자원 삭제

```bash
docker compose down -v --rmi all --remove-orphans
```

노벨킵의 컨테이너, 전용 네트워크, DB 데이터 Volume과 서비스 이미지를 제거합니다.

## 4. 사용자 경험(UI/UX) 설계

### 타겟 환경

- 독자: 출퇴근 중 모바일로 작품을 읽고 펀딩 현황을 확인
- 작가: PC에서 작품·회차·권·펀딩을 관리하고 모바일로 현황 확인
- 관리자: PC에서 통계와 처리할 주문을 우선 확인
  - (현재) 운영자는 `/admin`·`/admin/orders`·`/admin/fundings`

### 화면·흐름 판단

- 별도 랜딩에서 체험 역할을 고른 뒤에만 서비스에 들어가게 한다. 역할 없이 공개 작품만 보는 경로는 두지 않아, 심사·데모에서 역할별 메뉴와 소유권을 같은 흐름으로 확인할 수 있다.
- 역할별로 고정 체험 회원 1명을 두고 재선택해도 같은 회원을 세션에 연결한다. 재접속 후에도 같은 소유 데이터를 이어서 볼 수 있다.
- 웹소설 탐색이 서비스 본체이므로 독자·작가는 같은 작품 탐색 메인을 보고, 작가에게만 내 작품 메뉴를 추가한다.
- 운영자는 `/admin`·`/admin/orders`·`/admin/fundings`만 사용하며 독자·작가 메뉴에 들어가지 않는다.
- 권한은 역할별로 분리한다. 작가는 독자 기능을 포함하므로 작가→독자 되돌리기 버튼은 두지 않는다.
- 독자는 `작가 권한 활성화 체험`으로 작가 고정 회원으로 전환할 수 있다. 실서비스에서는 펀딩 피해 방지를 위해 작가 전환에 엄격한 인증이 필요하지만, 과제에서는 인증 없이 체험만 제공한다.
- 독자→작가 전환은 **다른 고정 체험 회원으로 세션이 바뀌므로** 독자 시점의 즐겨찾기·추천(및 향후 댓글)이 작가 체험에 이어지지 않는다. 데이터 연속성 테스트 중에는 역할 전환을 권장하지 않는다.
- 독자 화면을 다시 보려면 `역할 변경`(로그아웃) 후 랜딩에서 독자를 다시 선택한다.
- 역할 카드에 기본 선택을 두지 않고 마우스 오버·키보드 포커스 중인 카드만 강조한다.
- 사용자 선호에 따라 라이트·다크 모드 전환을 제공한다. 최초 방문은 라이트 모드이며 선택값은 브라우저에 저장한다.
- 작품 연재 상태(`SERIALIZING`/`COMPLETED`)와 공개 여부(`PUBLIC`/`PRIVATE`)를 분리한다. 새 작품 기본값은 미공개다.
- 공개 탐색(`/novels`)은 독자·작가에게 공개 작품만 보여 주고, 내 작품 관리(`/writer/novels`)는 소유 작품만 별도 화면으로 다룬다.
- 연재 상태 필터는 `연재 중`(부 완결 포함)·`부 완결`·`전체 완결`로 구성한다. 배지는 최신 완결 부 번호(`1부 완결`)를 표시한다.
- 별도 한 권/여러 권 상태나 권 수 컬럼 없이 실제 권(부) 행 개수로 권 수를 표시하며, 각 부와 소장본 한 권을 1:1로 대응한다.
- 부·회차 관리는 **작품 상세**(`/novels/{id}?from=writer`)가 주 동선이다. 회차 작성·수정은 전용 화면, 목록에서는 일괄 공개/미공개/삭제를 지원한다. 회차 공개 전환은 부·작품 완결 상태를 자동으로 바꾸지 않는다.
- 회차 열람은 `/episodes/{id}`이며 독자는 공개 회차만, 소유자·관리자는 미공개 회차도 볼 수 있다. 미공개 권의 회차는 독자에게 404다.
- 회차 목록은 최신화가 위이며, 각 화 옆에 댓글 수 `(N)`을 표시한다. 댓글은 대댓글 1단까지, 삭제는 소프트 삭제다.
- 작품 추천은 회원당 1회 토글이며 공개 작품만, 자신의 작품은 추천할 수 없다. 추천 수 변경은 작품 `updated_at`을 바꾸지 않아 최신순이 흔들리지 않는다.
- 내 즐겨찾기는 회원당 공개 작품 1회 토글이며 독자 메뉴와 `/novels?favorite=true`로 확인한다.
- 추천·즐겨찾기·검색·페이지네이션은 AJAX로 부분 갱신해 스크롤·화면 위치를 유지한다. JS 실패 시에는 기존 전체 새로고침으로 동작한다.
- 랜딩을 제외한 모든 화면은 같은 상단 탭·역할 메뉴·다크모드·맨 위로 버튼을 유지한다.
- 독자 화면은 모바일 우선으로 구성하고 웹소설 본문 너비와 줄 간격을 제한한다.
- 내부 상태 코드 대신 `연재 중`, `1부 완결`, `접수`, `배송중`처럼 이해하기 쉬운 한국어를 사용한다.
- 빈 목록·입력 오류·잘못된 상태 변경에 다음 행동을 안내한다.

### 의도적으로 넣지 않은 기능

- 실제 로그인·회원가입·비밀번호 인증 (과제 범위 밖이며 콘텐츠·펀딩·주문 흐름 검증에 집중)
- 실제 결제·환불·배송
- 실제 인쇄 API와 PDF 조판
- 좋아요·서버 푸시 알림·고급 검색
- 작가→독자 되돌리기 버튼 (작가는 독자 기능을 포함하므로 불필요)

### 주요 화면 캡처

## 5. 기술 스택 및 아키텍처

### 기술 스택

- Backend: Java 21, Spring Boot 4.1.0, Spring Data JPA
- Frontend: Thymeleaf, JavaScript, Bootstrap 5.3.8, HTML/CSS
- Database: MariaDB 11.8.8 LTS
- Build: Maven 3.9.16
- Runtime: Docker Compose

### 선택 이유

- Java 21: 최신성과 운영 검증 기간의 균형이 좋은 LTS
- Spring Boot 4.1.0: Java 21을 지원하는 신규 프로젝트용 최신 안정 버전
- Maven 3.9.16: 작은 단일 프로젝트에 충분하고 명시적인 설정을 설명하기 쉬움
- JPA: 작품·회차·펀딩·주문의 CRUD와 연관관계 구현량을 줄일 수 있음
- MariaDB: 사용 경험이 있고 공식 Docker 이미지로 동일한 실행 환경을 제공할 수 있음
- Thymeleaf: 별도 프론트 빌드 없이 목록·상세·입력 폼 중심 화면을 서버 렌더링할 수 있음
- Bootstrap: 기성 반응형 컴포넌트로 기능과 사용자 흐름 구현에 집중할 수 있음
- Docker Compose: 심사자가 로컬 Java·Maven·MariaDB 설치 없이 동일 환경으로 재현 실행할 수 있음

### 아키텍처

```mermaid
flowchart LR
    U["사용자 브라우저"] --> A["Spring Boot 앱 컨테이너"]
    A --> C["Controller"]
    C --> S["Service"]
    S --> R["Spring Data JPA Repository"]
    R --> D["MariaDB 컨테이너"]
```

- Java 패키지는 수정할 기능을 쉽게 찾도록 `com.novelkeep.{도메인}.{계층}` 구조 사용
- 주요 도메인: `home`, `member`, `novel`, `funding`, `order`, `admin`
- 각 도메인 내부에 필요한 `controller`, `service`, `repository`, `domain`, `dto`만 생성
- Docker 내부 앱 연결: `db:3306`
- IDE에서 실행한 앱 연결: `localhost:3307`
- DB healthcheck 통과 후 앱 컨테이너 시작
- Hibernate `create-drop`으로 스키마를 재생성하고 `DemoDataInitializer` 한 곳에서 목 데이터를 자동 적재

- Cursor AI로 과제 안내 분석, 서비스 기획과 사용자 페르소나 정의
- 요구사항·화면 흐름·ERD 초안 생성 후 사용자 검토로 수정
- 기술 스택 비교와 버전 호환성 확인
- Java·Maven·Docker 환경 설치와 실행 명령 검증
- Dockerfile·Compose 작성과 앱·DB 연결 및 Volume 지속성 검증

### 긍정적 활용

- 기획 대안을 빠르게 비교하고 사용자 판단 근거를 문서화
- 공식 문서와 실제 명령 실행으로 환경·버전·Docker 동작 검증
- 반복 작업과 설정 오류를 빠르게 발견하고 수정

### 실패·수정 경험

- 확정 전 주제와 기술을 확정된 것처럼 안내해 승인 절차를 다시 정리
- 인증 제외를 회원 데이터 제외로 잘못 해석해 ERD에서 회원을 누락
- 랜딩·공통 메인·역할별 화면 구분을 잘못 이해해 화면 정의를 반복 수정
- 역할 선택마다 회원을 생성했다가 고정 체험 회원 방식으로 수정
- 역할만으로 소유권을 구분하려다 회원 ID가 필요함을 재확인
- Docker의 호스트·컨테이너 경계를 불명확하게 설명해 실행 흐름을 다시 정리
- 불필요한 Maven Wrapper를 추가했다가 Docker 빌드 구조에 맞춰 제거

상세 기록은 [AI 활용 및 시행착오](docs/03_AI_시행착오.md)에 정리합니다.

## 7. 설계 의도

### 서비스 아이디어 선택 이유

- 웹소설은 책 제작 없이도 독립적으로 소비되는 콘텐츠여서 콘텐츠 서비스가 본체라는 조건에 맞음
- 완결 조건부 펀딩으로 독자의 미완결 구매 위험을 줄이고 작가의 완결 동기를 만들 수 있음
- 연재 콘텐츠를 종이책 제작 주문으로 자연스럽게 연결할 수 있음

### 사업적 가능성

- 스위트북 Book Print API를 도입할 웹소설 플랫폼 형태의 B2B 파트너 사례로 확장 가능
- 사전 펀딩으로 실수요를 확인해 작가와 플랫폼의 재고 위험을 줄일 수 있음
- 소규모 팬덤을 가진 독립 작가에게 추가 수익과 소장본 제작 기회를 제공할 수 있음

### 데모·권한 설계 의도

- 과제에서 회원 인증을 제외한 이유는 콘텐츠·펀딩·주문 핵심 흐름 검증에 집중하기 위함이다.
- 역할별 고정 체험 회원은 회원가입 없이도 소유권을 반복 검증하고, 같은 역할로 다시 들어와도 데이터를 이어 보기 위함이다.
- 실서비스에서는 펀딩 피해 방지를 위해 작가 전환에 본인·활동 인증이 필요하지만, 과제에서는 체험 전환만 제공한다.
- 역할 선택은 보안 인증이 아니며, 실제 서비스 적용 시에는 별도 인증·인가가 필요하다.

### 시간이 더 있다면 추가할 기능

- 문피아·조아라·노벨피아 등 외부 플랫폼 작품 연동
- 실제 결제·환불과 인쇄 API 연결
- 표지·판형 선택과 책 미리보기
- 알림·댓글과 독자 커뮤니티
- 작가 정산과 배송 추적
- 실서비스용 작가 전환 인증
